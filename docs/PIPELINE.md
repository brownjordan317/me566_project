# Pipeline reference

How the reconstruction pipeline works, what each part does, the conventions it relies on, and what has been measured. This is the working reference for development: **update it in the same change whenever a stage, default, output or key result changes.** The user-facing guide is `README.md`; this file is the engineering view.

Last updated: 2026-10-12.

## Goal and constraints

- **Input:** an ordered RGB image sequence (or video) of one object plus a binary object mask per frame. `make construct` generates masks with BiRefNet when the user supplies none (`recon/masks/birefnet.py`); benchmarks use the datasets' masks. External mask generators plug in only through `SCAN_MASK_COMMAND`. No camera calibration is assumed. Dataset intrinsics and poses are used only for evaluation and diagnostics.
- **Output:** an object mesh, a full-scene mesh, and coloured point clouds of the object and scene, all as 32-bit binary PLY.
- **Benchmarks:** MobileBrick (18 test scenes, phone captures, CAD reference meshes) and DTU (15 scans, robot-arm camera, laser-scan references).
- **Licences:** non-commercial models are allowed (research project), but each must sit in its own swappable stage and be listed in the README licence table. Weights are downloaded by `make setup` and never committed. Code from non-commercial repositories is never copied into `recon/`.
- **Citations:** any code ported from, or behaviour reimplemented after, another project is credited in its docstring (repository, file, licence, copyright) and in `THIRD_PARTY_NOTICES.md`. Method ideas are cited in docstrings and in the README "Credits and citations" section.
- **Data:** datasets live on the data drive (`/media/megrad/Data_Storage1/datasets`, symlinked into `runs/real/`). Runs and derived data live on the system drive under `runs/`.

### Component slots

Every stage hands the next one files in a fixed format (COLMAP text models for cameras, `<frame>_grounded.npy` depth, PNG masks, PLY meshes), so any component that reads and writes them can fill a slot. Pretrained models are used as pinned libraries; techniques taken from other work are reimplemented in `recon/` and credited. Slots and their Makefile settings:

| Slot | Setting | Components |
|---|---|---|
| Masks | `SCAN_MASKS`, `SCAN_MASK_COMMAND`, `SCAN_COMPLETE_MASKS`, `SCAN_REFINE_MASKS` (construct) | BiRefNet (default for captures), your own, SAM-HQ refinement |
| Keypoints | `FEATURES` | SuperPoint (default), ALIKED, SIFT; matched by LightGlue |
| Cameras | `CAMERAS`, `CAMERA_ROUNDS` | `colmap` (incremental mapping, default), `omega` (VGGT-Ω's one-pass cameras, fixed), `omega_ba` (Ω's cameras + bundle-adjustment rounds) |
| Camera model | `CAMERA_MODEL`, `REFINE_PP`, `PER_FRAME_FOCAL`, `INTRINSICS=dataset` | one or two focals, principal point, per-frame focal |
| Depth candidates | `DEPTH_MODEL`, `OMEGA`, `FUSION` | VGGT (default), DA3 (fusion), VGGT-Ω (replacement or third candidate), MoGe (background) |
| Depth adaptation | `ADAPT` | DA3 head fine-tuned on the scene |
| Refinement | `REFINE`, `REFINE_PASSES` | plane sweep, 1 pass (3 being confirmed) |
| Object surface | `OBJECT_TSDF`, `OBJECT_SUPPORT`, `VGGT_MASK_VOTE`, `OBJECT_EDGE_BAND` | weighted object TSDF (default), scene TSDF |

### Piece-by-piece selection

The pipeline is assembled from the best single piece for each job, whichever library it comes from, with no per-scene training. Each library's outputs are separate pieces (VGGT: cameras, depth, point maps, tracks; VGGT-Ω: cameras, depth and confidence; DA3: depth, rays and cameras, and it accepts known cameras; MoGe: point maps, normals, metric scale; COLMAP: triangulation and bundle adjustment; LightGlue: matching; BiRefNet: masks). Each piece is scored on its own against ground truth, not only through the final mesh:

| Job | Candidate pieces | Scored by | Best so far |
|---|---|---|---|
| Masks | dataset, BiRefNet, SAM-HQ refinement | final mesh | BiRefNet, level with the dataset's masks |
| Keypoints | SuperPoint, ALIKED, SIFT | pose error | SuperPoint |
| Matching | LightGlue, VGGT track head | pose error | LightGlue (track head untested) |
| Focal length | COLMAP self-calibration, VGGT, VGGT-Ω, DA3, MoGe | focal error against the calibration (`diagnostics/focal_sources.py`) | COLMAP (no learned estimate or average beats it) |
| Starting poses | COLMAP incremental mapping, VGGT-Ω, GLOMAP global mapping | pose error after bundle adjustment | COLMAP and VGGT-Ω equal (jeep 0.84 / 0.85 mm); GLOMAP fails on object orbits |
| Pose refinement | COLMAP bundle adjustment | | only candidate |
| Object depth | VGGT, DA3 (given our cameras), VGGT-Ω, MoGe | per-pixel error (`diagnostics/fusion_ceiling.py`) | DA3 alone; VGGT+DA3 photometric choice beats either |
| Depth refinement | plane sweep (ours), COLMAP PatchMatch geometric consistency (seeded with ours) | per-pixel error, mesh | plane sweep then seeded PatchMatch (per-pixel; mesh being tested) |
| Classical stereo candidate | COLMAP PatchMatch from scratch | per-pixel error | accurate but 600 s; seeding is better and 20× faster |
| Surface | weighted object TSDF, 2DGS | mesh | TSDF |

## Stages in detail

### 1–2. Cameras (`recon/cameras/`)

- **Features** (`matching.py`): SuperPoint keypoints on the full-resolution dataset images (`FEATURE_FRAMES`), at scales 1 and 0.5 (`FEATURE_SCALES`), up to 2048 per scale (`MAX_KEYPOINTS`). Fine scales add precision; coarse scales stay matchable on repetitive texture.
- **Pairs:** COLMAP-style sequential pairs, 10 neighbours plus power-of-two jumps. `LOOP_PAIRS=1` also wraps the sequence end to its start. It was benchmarked as neutral and is off.
- **Matching:** LightGlue, raw matches imported into a COLMAP database (`sfm.py`). Geometric verification runs in parallel `matches_importer` processes on database copies. The WAL checkpoint before copying is required, or the copies are empty.
- **Mapping:** the COLMAP 3.9 mapper (`/tmp/colmap-local`, library path exported by the Makefile). Global bundle adjustment ratios are 1.4 (29% faster, same accuracy). There is one shared SIMPLE_PINHOLE focal, and the principal point stays at the centre.
- **Per-frame focal** (`PER_FRAME_FOCAL=1`, MobileBrick default): split cameras, then bundle-adjust focal lengths per frame. It tracks phone focus breathing (true range about 1.6%, correlation 0.82). DTU's fixed lens must use `PER_FRAME_FOCAL=`, because per-frame focal invents drift there.
- **Rescale:** the model is solved at feature resolution, then rescaled to the working frames (`rescale_text_model`).
- **Reference substitution** (`reference.py`, diagnostic): reference poses at map scale, cameras from the database (true K with `INTRINSICS=dataset`), re-triangulated, rescaled to working frames.

### 3–9. Depth (`recon/depth/`)

- **Grounding** (`grounding.py`): every prediction is fitted to the sparse COLMAP points observed in that frame, with a robust scale-and-shift fit. Object depth uses object-mask anchors; background uses all anchors. Frames are rejected when the fit collapses: `scale_share < 0.5` for metric models, or relative anchor error above 3% (`candidates.py`, `da3.py`).
- **MoGe-3** (`monocular/moge.py`): single-image depth from the full frame. Object-anchored output goes to `moge_raw`, scene-anchored to `moge_scene`, the background source. Frames with fewer than 30 object anchors are skipped, not fatal.
- **VGGT** (`multiview/vggt.py`): multi-view depth in windows of 16 frames, step 8. `unpad_depth` inverts VGGT's padding. Grounded with object anchors.
- **Combine** (`combine.py`): VGGT depth inside the mask, MoGe-scene depth outside. This is the "hybrid".
- **DA3** (`multiview/da3.py`): DA3-Giant fed our COLMAP extrinsics (4×4 world-to-camera) and intrinsics. It returns depth within about 2% of map scale, which is then grounded. Windows of 16, step 8, input resolution 756 (`DA3_RES`), about 0.3 s per frame. 756 beat 504 on all four development scenes: per-pixel median 6–12% and p90 11–17% lower, fused-mesh p90 5–11% lower, coverage up 0.2–2 points. 1008 runs out of memory on 24 GB, even with 8-frame windows.
- **Cross-scene DA3 head (experimental, research only, 2026-10-29)** (`multiview/da3_distill.py`): the first student of the distillation plan. DA3-Giant's backbone stays frozen; its DPT depth head is trained on the MobileBrick training split (true cameras, depth rendered from the true mesh; never test, DTU or T&T). Windows of 16 at 756 px, features through `da3_adapt.window_features`, 4 head steps per window of 4 frames, Adam 1e-5. Loss: scale-invariant log-L1 on true-depth pixels (surface-to-surface depth jumps dropped, silhouettes kept) plus 0.1 × log-L1 to the frozen original head elsewhere. Every 8th set number is held out whole for validation. Output: `runs/models/da3_distill/<name>.pt`, loaded by `da3.py --head-weights`. Not in the Makefile. First run (`gt_v1`, 117 training scenes, 18 held out): held-out median-scaled depth error 2.58 → 1.74 mm after epoch 1 and 1.67 mm after epoch 2 (p90 10.26 → 6.19), 18 of 18 held-out scenes better; epoch 3 stopped out of GPU memory when another job shared the card, so the epoch-2 weights are kept. Dev-scene comparison with plain and per-scene adapted DA3: `runs/real/dev/distill/score_dev.sh`. Dev scenes, per-pixel error on object pixels (`diagnostics/fusion_ceiling.py --extra`, median / p90 mm), plain DA3 → student → per-scene adapted: jeep 1.24 / 3.73 → 1.09 / 3.23 → 0.93 / 2.94; audi 1.29 / 4.00 → 1.22 / 4.04 → 0.99 / 3.48; convertible 2.14 / 8.71 → 1.66 / 7.93 → 1.45 / 8.81; big_ben 2.79 / 10.59 → 3.03 / 10.53 → 2.55 / 10.05. The student beats plain DA3 on three scenes with no per-scene work (convertible −22%, and the lowest p90 of all three there) but is worse on big_ben (+8%; the training split is small LEGO sets, big_ben is the largest dev object); per-scene adaptation still wins on median everywhere. Next: per-scene adaptation started from the student head.
- **Learned judge (experimental, 2026-10-29)** (`judge/`): learns to choose between depth candidates from any source, so a better model later just joins the pool. Not in the Makefile yet.
  - **Evidence** (`judge/evidence.py`), computed on every 4th working pixel over the dilated mask; the judge is never told a candidate's source:
    - own: per-view slanted NCC against 6 neighbours (sorted), silhouette share over 12 spread reference views, facing, roughness, slope;
    - per pair of candidates: support and free-space violation of one's point by the other's depth in the reference views (the diagonal is self-consistency);
    - image: colour, local contrast, highlight, mask.
    Pair evidence is combined (`combine_pairs`: depth relative to the set's median, share agreeing, mean/max support, mean violation) only once the candidate set is chosen, so a left-out source leaves no trace.
    - self-report (optional, 2026-10-30): a source that can check itself writes `<frame>_selfcheck.npz` beside its depth (confidence, residual, normal disagreement; `SELF_FEATURES` adds `self_present`). The Gaussian pass's comes from `recon/depth/gaussian_selfcheck.py`, which re-renders the exported surfels (re-rendered depth identical to the pass's, median relative difference 0): opacity, |render − photo| blurred 5×5, and 1 − cos between surfel and depth normals. On jeep the opacity is about 1 everywhere (p5 0.97), but residual and normal disagreement track error: Spearman 0.18 / 0.25 with |error|, and the worst 10% by normal disagreement has a median error of 0.83 mm against 0.36 for the better half. `judge/self_reports.py` adds them to judge data written before they existed (`<frame>_self.npy`); the dataset writes them itself.
  - **Synthetic candidates** (`judge/corrupt.py`): true depth with per-frame drift, a world-fixed smooth bias, a per-view smooth bias, and 1–3 of regional offsets, softened edges, lost thin parts, floaters, holes, highlights pushed behind, lumps, edge bleed. Tuned so their errors overlap real models' (jeep: synthetic medians 0.8–2.6 mm, p90 1.5–8.3; VGGT/DA3/ViGeo/π3X 1.3–2.2, p90 3.9–7.5); the first version was too clean (0.4–0.6 mm) and too self-consistent, which would let the judge spot "synthetic" instead of judging evidence.
  - **Data** (`judge/dataset.py`): per training scene, the evidence of every candidate and the true depth rendered in our cameras (reference placed as the shape metrics place it); about 2 s and 0.9 MB per frame.
  - **Network** (`judge/network.py`): shared 3-level U-Net per candidate, then per-pixel attention across candidates with a learned "none" token (a set transformer, no positional encoding), so any number and order of candidates work; a confidence head.
  - **Appearance and full-resolution photo (2026-10-30, testing):** inputs on the 240×180 grid (1/8 of a 1920×1440 photo) could not fit even the training scenes (v3ns picks the best source 54.3% of the time on training sets against 54.0% held out). On held-out pixels, where the best source beats the next by over 3 mm (10% of pixels) the judge is still wrong 25% of the time, and those pixels carry 37% of its regret against the oracle; on the 71% where sources are within 1 mm it is near chance at little cost. `judge/appearance.py` adds DINOv2 ViT-L/14 features of the full-resolution photo (Apache-2.0, local hub cache), projected onto 64 principal components fitted on training-split photos only (`runs/models/judge/appearance.npz`, saved into the weights), written as `<frame>_appearance.npy` and resampled onto the grid; `train.py --appearance`. `--photo` adds a learned branch (`network.PhotoStem`, three stride-2 stages, 32 channels) that reads the full-resolution photo down to the grid. Weights trained with either are saved with their configuration (`{'config', 'state', 'projection'}`), which `apply.py` reads.
  - **Training** (`judge/train.py`): random crops, random candidate subsets (1 to all); loss = soft cross-entropy towards candidates near the truth (exp(−error / 0.5 mm)) or "none" when nothing is within 3 mm, + 0.5 × the expected error of the choice, + 0.2 × confidence BCE; pixels weighted up where candidates disagree and most where a minority is right. `--exclude` keeps sources out of training; validation then reports how often the judge picks a never-seen source where it is best. Held-out set groups as in `da3_distill`. Validation compares with the fusion's own rule (best-3 NCC pooled) and the oracle. Since 2026-10-30, a term on the judged surface: `--smooth-weight` (0.2) × half the L1 change of the choice between neighbouring pixels with the same candidates, down-weighted across colour edges, against the patchwork of per-source biases. Real self-reports are dropped from 30% of samples; synthetic candidates get an honest-but-noisy report (worse where their error is larger), an uninformative one or none, a third each, so bringing a report is no sign of being right.
  - **Apply** (`judge/apply.py`): scores optionally averaged over `--smooth` grid pixels, upsampled to the working frame; the top candidate is kept and averaged only with candidates within `--agree` (0.003; 0 = top pick alone) of it (never across two surfaces); "none" is marked in `<frame>_none.png` and, with `--abstain keep` (default since 2026-10-30), still takes the top candidate's depth: leaving it empty lost an 8% piece of space_shuttle (on that piece the judge abstained on 37% of the pixels the Gaussian depth had right and picked a wrong surface, mostly MoGe, on 12%; the TSDF then dropped the thinly supported part, official chamfer 5.24 → 12.55 mm, recall at 5 mm 85.6 → 80.2%). Writes `_grounded.npy` and `_confidence.npy` like the fusion filter; reads self-reports when the weights were trained with them (v1 was not).
  - **Training pool** (`runs/real/train_pool/pool.sh`, on the data drive): the default pipeline on every training scene with intermediates kept, then judge data for VGGT, DA3, MoGe (object-anchored), the Gaussian pass and the refined fusion plus 4 synthetic candidates, every 2nd frame. ViGeo and π3X are kept out of training on purpose: on the dev scenes they are the never-seen sources of the leave-one-out test. Pool of 2026-10-29: 134 of 135 scenes (2492_8911_9282 failed: broken poses, MoGe anchor error about 2,000 map units, then a TSDF volume overflow), 3,585 frames, about 2.5 min a scene per pass; the Gaussian pass about 2 min of that.

- **Fusion filter** (`fusion/filter.py`): for VGGT and DA3, scores each candidate's depth on a stride-2 grid of object pixels by photometric NCC (`fusion/photometric.py`).
  - Patches are 9×9 at full resolution, compared against the 6 most similar views, with the best 3 averaged.
  - Scores are pooled over 17×17 working pixels, plus a per-model prior (0 for both).
  - Each object pixel takes the winner's depth; mask pixels without a candidate are cleared.
  - It also writes `*_confidence.npy`, the margin of winner over runner-up.
- **Refinement** (`fusion/refine.py`): plane sweep of ±0.6% in 13 steps around the fused depth.
  - NCC with slanted patches (normals from the fused depth), aggregated over 15×15, a quadratic penalty of 0.02, and parabolic sub-step interpolation.
  - A pixel moves only if its gain exceeds 0.01.
  - Neighbours are taken 10–35° away (`views.neighbours(band=...)`); close views can't resolve millimetres.
- **Consistency** (`consistency.py`): each pixel is projected into 24 reference views spread over the sequence. It's dropped if more views see through it than support it. The agreement tolerance is 1% (`CONSISTENCY_TOLERANCE`; was 3%, about 12 mm at jeep's distance, which let 1–3 mm-off depth into the TSDF).
- **VGGT-Ω experiment** (`multiview/omega.py`): `DEPTH_MODEL=omega` replaces VGGT; `OMEGA=1` adds Omega as a third photometric fusion candidate. Use a fresh `RUN` for each comparison. The gated checkpoint is cached through Hugging Face. Omega runs up to 128 frames in one pass by default; overlapping windows are grounded separately before averaging. The default remains VGGT + DA3. `grounding.ground` (affine fit in depth or inverse-depth space) is shared by DA3 and Omega.
- **Removed 2026-10-12** (rejected experiments; findings below; code archived in `/media/megrad/Data_Storage1/me566_archive/2026-10-12_code_cleanup/project_before_cleanup.tar.gz`): single-image candidates (Depth Pro, Depth Anything V2, Marigold; `candidates.py`), smooth bias fields (`bias.py`), the agreement selector (`fusion/agreement.py`), MVInverse albedo (`fusion/intrinsics.py`), MapAnything and π³ adapters, the old MoGe patch refinement and propagation (`multiview/refine.py`, `propagate.py`), and the Makefile's `reconstruct-moge`, `reconstruct-dense`, `reconstruct-vggt-full` arms with their `evaluate-*` targets.

### 10–15. Surface (`recon/surface/`)

- **TSDF** (`tsdf.py`): Open3D VoxelBlockGrid on CUDA.
  - Voxel 0.02 map units, truncation 0.12.
  - `--min-views 3` (`SCENE_MIN_VIEWS`) keeps surface seen by at least 3 frames, which removes floaters.
  - The depth discontinuity filter `tau` is 0.03; depth range 0.5–30.
  - Hash capacity is 3× the estimated block count (minimum 100k) with a GPU memory check, because the CUDA hash map corrupts above about 45% load.
- **Weighted object TSDF** (`weighted_tsdf.py`): dense grid over the object's bounds, voxel 0.02, band 0.06 map units; per-pixel weight = VGGT–DA3 agreement (σ 1%) × viewing angle, plus `--confirmed-dir` (pixels PatchMatch's seeded geometric pass confirmed weigh 1, the rest `--unconfirmed-weight` 0.2; off by default). `OBJECT_TSDF_ARGS` passes extra options from make.
- **Object extraction** (`object.py`): crop the scene mesh to landmark bounds plus a 0.4 margin. Keep triangles whose depth-visible projections fall inside the mask in at least 80% of the views that see them (`VGGT_MASK_VOTE`, at least 2 views), then drop components under 300 faces, and components whose median mask-view count is under 25% of the largest component's (`OBJECT_SUPPORT`, `--min-component-support`). The support filter removes things a mask covered in only a few frames (BiRefNet's chair on big_ben: 8 views against 53); the report lists every component of 1000+ faces with its count. `OBJECT_EDGE_BAND` (`--edge-band`, default 0 = off; 8 measured best on the development scenes, 2026-10-28) lets a view abstain where a face lands within that many pixels of the mask's edge, when the face has at least 3 such clear views (`--clear-min`); see the finding below.
- **Masks** (`recon/masks/`): `birefnet.py` (default for `make construct`, MIT, pinned Hugging Face revision; `--guide` keeps only foreground pieces overlapping supplied masks), `sam_hq.py` (boundary refinement of supplied masks).
- **Cleanup** (`clean.py`):
  - **Object:** components below 1000 faces removed, holes up to 0.08 filled, 5 Taubin iterations.
  - **Scene:** pieces under 5% of the largest dropped, holes filled, no smoothing.
  - Written as 32-bit PLY (`common/ply.py`). Open3D's `fill_holes` result shares buffers with its tensor mesh, so the tensor mesh must be kept alive.
- **Denoising** (`denoise.py`, `DENOISE=1` default, `DENOISE_ARGS`): faces first oriented consistently (`igl.bfs_orient`), then bilateral normal filtering (Zheng et al. 2011; spatial scale 1 mean edge length, range 0.2, 4 iterations) over faces sharing a vertex, then 10 vertex updates onto the filtered planes (Sun et al. 2007). A vertex step that would turn one of its faces inside out is undone, repeated until none is.
- **Point clouds** (`points.py`):
  - Back-project the consistent depth; keep pixels that at least 3 other views see within 1%.
  - Voxel-average at 1/500 of the object diagonal (scene ×4), remove outliers, select the object by mask votes.

## Evaluation (`recon/evaluation/`)

- **MobileBrick** (`metrics/mesh.py`): the mesh is placed by a similarity fitted to our camera centres (Umeyama) and scored against the reference mesh vertices.
  - **Official:** surface median, p90 (distance from points sampled on our mesh to the reference *surface*, via Open3D ray casting), and coverage of reference vertices within 10 mm. Until 2026-10-10 accuracy used distance to the nearest reference *vertex*. The CAD meshes are remeshed at about 1 mm edges, so that floor scored the reference itself at 0.38 / 0.56 mm. Numbers in older notes or logs that predate the fix are inflated; re-score kept meshes with `recon.evaluation.metrics.mesh` (it needs the run's `poses/export/trajectory.csv`).
  - **Shape:** the placement is refined by scaled ICP (10 mm then 3 mm) before scoring. Shape median and p90 are the metrics to optimise.
  - `size_error_pct` is the scale removed, positive when ours is too large.
  - **F-scores** (added 2026-10-10): after shape alignment, `precision_{1,2}mm_pct` (our surface within τ of the reference), `recall_{1,2}mm_pct` (reference surface within τ of ours) and `fscore_{1,2}mm_pct`. Accuracy-only metrics reward deleting hard surface; use the F-score to judge accuracy/completeness trade-offs. Earlier sign confusion: the ICP scale maps ours onto the reference.
- **MobileBrick official protocol** (`metrics/mobilebrick.py`, added 2026-10-12, run by `make evaluate` into `metrics/object_official.json`): port of the benchmark's `evaluations/evaluate_3d.py` (MIT). Our mesh is placed by the camera-centre similarity, then the official steps: rigid ICP of reference vertices onto ours (2 cm, 10 iterations, applied only if fitness > 0.99), crop to the scene's `visibility_mask.npy`, 100k Poisson-disk samples per mesh, precision / recall / F1 at 2.5 and 5 mm, chamfer as the *sum* of both mean distances (reported in mm; the paper uses metres). `scaled_*` repeats it after our scaled ICP. Verified: the visibility crop matches the original torch `grid_sample` on >99.9999% of vertices (jeep, big_ben, castle). Compare these numbers, not our F@1/F@2, with published MobileBrick results.
- **DTU** (`metrics/dtu.py`): a port of DTUeval-python. Mesh sampled uniformly (not DTUeval's per-triangle grid), thinned to 0.2 mm, ObsMask and table plane applied, 20 mm cap. Chamfer is the mean of accuracy and completeness. `shape_chamfer_mm` repeats the score after scaled ICP. The official chamfer is the number to compare with published results.
- **Poses** (`metrics/poses.py`, `reprojection.py`): similarity-aligned camera position error, and a COLMAP projection audit.
- **Signed error** (`diagnostics/signed_error.py`, 2026-10-27): dents and bulges against the reference's outward normal after ICP-with-scale placement, split by viewing, with an overlay on the photographs.
- **Temporal consistency** (`diagnostics/temporal_consistency.py`, 2026-10-27): Video Depth Anything's TAE for every depth stage of a kept run, with `--scene` the reference's own floor.
- **Lost surface** (`diagnostics/lost_surface.py`, 2026-10-27): for reference surface the capture saw but the mesh misses, the first stage that dropped it (depth models, fusion, refinement, Gaussian pass, consistency, view count, TSDF, extraction, cut). Needs a run kept with `KEEP_INTERMEDIATE=1`.
- **Pose AUC** (`metrics/pose_auc.py`, added 2026-10-12, `metrics/pose_auc.json` from `make evaluate` / `evaluate-dtu`): relative-pose protocol of VGGT / DA3 / PoseDiffusion, reimplemented after DA3's `bench/utils.py` (Apache-2.0). All frame pairs: rotation error and translation-direction error (folded, scale-free); RRA@15, RTA@15, AUC@1/3/5/15/30 (mean over 1° thresholds of the share of pairs whose larger error is below). AUC@30 saturates on our data (≥99%); AUC@1 and AUC@3 discriminate.
- **Tanks and Temples** (`metrics/tnt.py`, added 2026-10-12): port of the official python_toolbox evaluation (MIT) to current Open3D (`o3d.pipelines.registration`), in 2DGS's variant that scores mesh vertices plus face centres. Our camera centres are RANSAC-registered (with scale) to the reference COLMAP trajectory moved by `_trans.txt`, refined by three scaled ICPs in the crop volume, then precision / recall / F at the scene's τ after τ/2 voxel downsampling. Frames match by order (frame i ↔ image i+1 of the image set). Validated on T&T's own COLMAP reconstruction of Barn with its own trajectory: precision 45.6, recall 55.2, F 49.9 at τ = 1 cm, all 410 frames matched.
- **Diagnostics** (`diagnostics/`):
  - `stage_ranking.py` (`make stage-ranking`): reconstructs each scene with ours, truth poses, truth depth, and both.
  - `oracle_depth.py`: renders reference depth into our cameras. `--refine-to OUR_MESH` places the reference by surface fit. Without it, MobileBrick's pose-versus-CAD scale mismatch biases reference depth by up to 3 mm.
  - `reference_surface.py`: Poisson surface from a DTU point cloud, written in metres to `runs/real/dtu_reference_surfaces/`.
  - `recall_loss.py`: assigns each missed reference point to its first failing stage (unobserved, outside mask, cross-view check, inaccurate depth, meshing). Removed in the morning cleanup of 2026-10-12 and restored the same day for the recall work; run it on a run kept with `KEEP_INTERMEDIATE=1`.
  - Removed 2026-10-12 (one-off investigations, findings kept below; archived as above): `complementarity.py`, `depth_consistency.py`, `missing_surface.py` and the `diagnose-*` targets.
- **Benchmark** (`benchmark/run.py`, `make benchmark`): a rich dashboard, two scenes in parallel (`BENCH_JOBS`), a GPU lock file serialising GPU stages. `BENCH_SCORES_ONLY=1` (`--scores-only`) builds only what scoring needs, skipping texture, point clouds and the scene mesh (texturing castle's 900k-face mesh took over 17 minutes). Two parallel scenes gain little when both are GPU-bound: each GPU stage roughly doubles while waiting on the lock (aston: 466 s shared vs about 215 s alone). `summarize.py` writes `summary_<metrics>.md`/`.csv`.
- **Comparison** (`benchmark/compare.py`, added 2026-10-12): repeated default runs give each metric's mean ± sd over runs and the median per-scene sd (the noise floor); each ablation arm is paired with default run 1: mean, difference, scenes better/worse, Wilcoxon signed-rank p.
- **Timing** (`benchmark/timing.py`, added 2026-10-12): every Makefile stage appends `<unix time>\t<label>` to `RUN/timing.log` (the `stage` macro); stage time is until the next stage starts, reconstruction ends where scoring starts. With a GPU memory log (`<time>\t<GiB>`, sampled by `cudaMemGetInfo` because NVML can be unavailable) it reports peak memory per stage above idle. Profile runs use `BENCH_JOBS=1` so stages don't wait on the GPU lock.
- **Baselines** (`baselines/`, comparison only, added 2026-10-12):
  - `vggt_feedforward.py`: one VGGT-1B pass over the sequence (≤96 frames, evenly spread) for cameras, intrinsics and depth; written as a COLMAP text model + trajectory + depth (rescaled to median depth 6.5), then our scene TSDF, mask-vote extraction (vote 0.8, support 0.25) and cleanup. Placed by VGGT's camera centres for scoring.
  - `pi3_feedforward.py` (2026-10-28): the same with π³X (one forward pass, ≤96 frames, images resized to π³'s ~255k-pixel grid; depth from the local points, intrinsics from their rays), then the same meshing. Comparison only (Pi3X weights CC BY-NC 4.0).
  - `pgsr.py` (2026-10-13): PGSR from `third_party/PGSR` (commit de24f1a, research and non-profit use only) in the 2DGS venv, its `diff-plane-rasterization` built with the 2DGS flags; PGSR imports only `pytorch3d.transforms.quaternion_to_matrix`, so the venv has a one-function stand-in instead of pytorch3d. Reuses the 2DGS wrapper's workspace and mask culling. Recipe as PGSR's `scripts/run_dtu.py` (`--ncc_scale 0.5`, our frames already at its `-r 2` size, TSDF voxel 0.002 normalised), or a warm start (`--init-points` our dense clouds, `--train-args` to start its geometric losses early).
  - `pgsr_train.py` (launcher, runs PGSR's train.py unchanged): GPU pixel sampling (default), and with `pgsr.py --depth-prior DIR --depth-weight W` a depth-prior term after DRGS (Chung et al., CVPR workshops 2024; our implementation): the wrapper writes our depth into PGSR's frame per view (object pixels; normalised, principal point centred, cropped like the images), the launcher wraps PGSR's `render` (keeping the iteration's training-view render and requesting its plane depth from the first iteration) and `torch.Tensor.backward` (adding W × the mean relative depth difference to train.py's loss). Alignment check, scan24, 1k iterations: rendered depth and prior agree to 0.06% median. Prior = our 1-pass refined depth, 3k iterations, our meshing; chamfer scan24 / 37 / 63 (no prior 0.418 / 0.672 / 0.713, mean 0.601): W 0.3 0.416 / 0.652 / 0.729 (0.599); W 1 0.411 / 0.637 / 0.760 (0.603); W 3 0.413 / 0.623 / 0.776 (0.604). It helps where our depth is right and the photos are weak (scan37 −7% at W 3) and drags PGSR towards our errors where our depth has bad frames (scan63, whose sparse grounding was off: refined p90 9.7 mm). `--depth-clip C` caps each pixel's relative difference (a robust prior). At W 3: prior from the loop-1 depth 0.414 / 0.623 / 0.760 (0.599); 0.5% cap 0.418 / 0.641 / 0.730 (0.596). scan63 is worse in every version, by accuracy (1.03 → 1.08–1.13 mm). It is not the less textured scene that gains: object gradient median scan24 / 37 / 63 = 2.1 / 5.4 / 2.3 grey levels, so a texture gate (`--texture-gate G`, weight exp(−gradient/G)) leans hardest where it hurt. Fading prior (`--depth-decay 2000`, linear to zero by iteration 2000): 0.413 / 0.634 / 0.749 (0.599). Texture gate at G = 2: 0.409 / 0.642 / 0.761 (0.604); rejected and removed. Every variant helps scan37 and hurts scan63, and the means stay within 0.005 of no prior: the prior steers PGSR into a worse solution early on scan63 even when it fades. Scene-dependent and neutral on average, so not adopted as a fixed setting; `--depth-prior/-weight/-clip/-decay` remain in the academic wrapper (a per-scene choice by the held-out judge would need a second PGSR run per scene).
  - Both Gaussian baselines ignore the principal point (they assume the image centre): since 2026-10-13 the 2DGS workspace shifts each frame to centre it and crops (DTU's is about 12 px off at 800 px); without it, 2DGS with the dataset's cameras put scan24's surface about 3 mm off (chamfer 2.86 mm). Earlier 2DGS runs used our cameras, whose principal point is the centre, so they were unaffected.
  - `twodgs.py`: 2DGS trained on *our* cameras and sparse points (same-camera comparison), run from `third_party/2d-gaussian-splatting` in its own venv (`~/.venvs/me566-2dgs`, PyTorch 2.7.1 + CUDA 12.8, because the system nvcc is 12.9 and our PyTorch is CUDA 13). The 2DGS paper's DTU recipe: unit-sphere normalisation from our object landmarks, 30k iterations, `--depth_ratio 1 --lambda_dist 1000`, TSDF voxel 0.004 / trunc 0.016, largest cluster, then their DTU mask culling (24 px dilation at 1600 px width, all views). Gaussian-Splatting licence: research/evaluation only. Building its extensions with GCC 13 / CUDA 12.9 needs headers its sources omit; without editing `third_party/`: `CUDA_HOME=/usr/local/cuda-12.9 TORCH_CUDA_ARCH_LIST=8.9 NVCC_APPEND_FLAGS="-include cfloat -include cstdint" CXXFLAGS="-include cstdint" ~/.venvs/me566-2dgs/bin/pip install --no-build-isolation submodules/{simple-knn,diff-surfel-rasterization}`. The 2DGS venv pins **Open3D 0.19.0**: 0.20's legacy `ScalableTSDFVolume` (which 2DGS meshes with) returns empty meshes even for a synthetic plane, while 0.19 works; our own TSDF uses the tensor `VoxelBlockGrid` and is unaffected. Our cameras are SIMPLE_PINHOLE and 2DGS only reads PINHOLE, so the wrapper rewrites them (same focal for x and y). A trained model is reused if meshing has to be redone. Test on DTU scan24 with our cameras: chamfer 0.888 mm (shape 0.676), 574 s training + 13 s meshing, against ours 0.63 (shape 0.36) in about 140 s; 2DGS's published scan24 with true cameras is 0.48. VGGT feed-forward on scan24: chamfer 3.22 (shape 0.85, size −3.1%) in 21 s; its rotations are slightly better than ours there (median relative error 0.28° vs 0.40°), its depth and scale are not.

## Conventions

- **Frames:** `frames/NNNNNNNN.png` (8 digits) at working resolution (MobileBrick 960×720, DTU 800×600). Masks: `masks/NNNNNNNN.png`. Full-resolution dataset images: `DATA/SCENE/image/NNNNNN.{jpg,png}` (6 digits). Match frames by integer stem.
- **Depth files:** `<frame:08d>_grounded.npy`, float32 z-depth in map units, 0 = no depth. Every depth stage directory also has a summary JSON, which the Makefile uses as its target (`moge_inference.json`, `vggt_inference.json`, `hybrid_depth.json`, `candidate.json`, `consistency.json`).
- **Poses:**
  - COLMAP text models store world-to-camera `R, t`; `common/colmap.parse_model` returns them that way.
  - `common/trajectory.load_poses` returns camera-to-world rotation and camera centre: `camera = (X - centre) @ R`, `X = camera @ R.T + centre`.
  - DA3 takes 4×4 world-to-camera matrices.
- **Map units:** COLMAP's arbitrary scale. Roughly 64 mm per unit on jeep. Metric thresholds in code are in map units unless named `_mm`.
- **Progress:** use `recon.common.progress` (`bar`, `spinner`, `done`, `heading`). `NO_PROGRESS=1` or a non-terminal gives plain log lines.
- **GPU lock:** every GPU stage runs under `flock $(GPU_LOCK)`. The camera stage takes it inside `solve.py` (`--gpu-lock`) only around SuperPoint/LightGlue, so COLMAP's CPU mapping doesn't hold the GPU; before 2026-10-12 it took no lock and failed with out-of-memory when another scene's DA3 (about 20 GB) was running.
- **Make:** intermediates are `.SECONDARY`. After the last goal, `PRUNE` deletes `depth/`, `work/` and pose scratch unless `KEEP_INTERMEDIATE=1`. GPU stages are prefixed with `$(GPU)` (flock). Command-line variables propagate to the benchmark's sub-makes.
- **Tests:** `make test` / `python3 -m pytest -q`, with `tests/` mirroring `recon/`. Keep all passing; add tests with new modules.
- **COLMAP:** 3.9.1, a user-space extraction of the Ubuntu package (and its missing libraries, without the GLES Qt build) in `~/.local/colmap-3.9.1`; the Makefile's `COLMAP_ROOT` finds it there (or the old `/tmp/colmap-local`) and exports `LD_LIBRARY_PATH`. `/tmp` is wiped on reboot, so nothing long-lived goes there.
- **Viewing outputs:** `make view_ply PATH=file.ply` (or `PLY=file.ply`; `recon/apps/view_ply.py`, 2026-10-12) opens Open3D's native GPU viewer (O3DVisualizer): full meshes and multi-million-point clouds without decimation, vertex or point colours, textures for `.glb`/`.obj`, height shading when uncoloured, settings panel for lighting and point size. A Plotly page was tried first and dropped as too slow for full-resolution outputs. `PATH=` on the make command line replaces the shell's search path for recipes, so the target restores the `PATH` make started with (`HOST_PATH`, captured at parse time) and calls `/usr/bin/env` by absolute path.
- **Dependencies:** pretrained models are libraries, not vendored code: MoGe, LightGlue, VGGT and SAM-HQ (`segment-anything-hq`) are pip packages pinned to the commits the results were measured with (`requirements.txt`); Depth Anything 3 is installed by `make setup` from its pinned commit with `--no-deps`. Nothing in the pipeline reads `third_party/`, which is git-ignored and holds only academic baselines (2DGS) and comparison checkouts. Switching from the old clones to these packages was verified on jeep: F@1 75.82 vs 75.78, shape median 0.362 vs 0.364 mm (run-to-run noise). What this project takes from other work is techniques, reimplemented in `recon/` and credited (THIRD_PARTY_NOTICES.md); copying model architectures in would add bulk without adding anything of ours, and VGGT's licence forbids it.
- **Python:** `python3` is the `~/venv-ardupilot` venv (PyTorch 2.13, CUDA 13). 2DGS has its own venv (see Baselines).
- **After a reboot:** the data drive is not in fstab; mount it with `udisksctl mount -b /dev/nvme0n1p1 --no-user-interaction` (back at `/media/megrad/Data_Storage1`), or every dataset symlink dangles and make tries to re-download. Long queues live in `runs/real/academic/` and run detached (`setsid nohup`).
- **Camera solver options** (2026-10-11, all off by default): `FEATURES=aliked|sift` (default superpoint), `CAMERA_MODEL=pinhole` (separate x/y focal), `REFINE_PP=1`. See Findings: none improved placement.

Shape chamfer is unchanged across the three, so the whole gap is placement, not surface quality. Where the placement error comes from (2026-10-11):
- Camera-centre residuals are lateral (across the view axis), 0.4–1.3 mm, with 0.1–0.2° orientation error: the pivot ambiguity of a narrow lens (DTU about 31° field of view, cameras about 630 mm from the object).
- The official alignment fits a similarity to camera centres only. Its rotation is weakly fixed by centres on a cap, and the 600 mm lever arm turns 0.06–0.34° into 0.5–3 mm at the object even with true intrinsics.
- Taking the rotation from the camera orientations instead (`mesh.pose_similarity`, reported as `pose_aligned_*` by `metrics/dtu.py`) gives 0.594 mm with true intrinsics: our poses are nearly as good as DTU's (0.556).
- With estimated intrinsics it fails (2.28 mm): DTU's principal point is (823, 619), about 30 px from the centre we assume, which tilts every estimated camera by the same 0.6°. Fitting a shared camera-frame rotation in the alignment recovers that bias (0.58–0.70° on every scan) but improves placement only modestly (median 1.34 to 1.23 mm).
- Self-calibration doesn't fix it: estimating the principal point (`REFINE_PP=1`) gets within 5–15 px but leaves pose error at 0.90 against 0.94 mm and hurts MobileBrick badly (jeep 0.84 to 4.19 mm); separate x/y focal (`CAMERA_MODEL=pinhole`, DTU's pixels are 0.3% non-square) and exhaustive pairs change nothing; ALIKED keypoints (`FEATURES=aliked`) cut the focal error on scan37/63/83 (−1.5/−1.1/−1.4% to −0.8/−0.65/−0.4%) but not pose error. ### Where the remaining error is

The stage ranking (all 18 MobileBrick scenes, `runs/real/mobilebrick_stage_ranking/`, scored with the old vertex metric; its poses were pruned, so it can't be re-scored) showed that truth poses change nothing and truth depth halves the error. Re-measured with the corrected metric on the development scenes (`runs/real/dev/<scene>/{oracle,default}`):

| Scene | Truth depth (meshing loss only) | Default pipeline |
|---|---|---|
| jeep | 0.085 / 0.361 | 0.340 / 1.252 |
| audi | 0.179 / 0.760 | 0.482 / 1.393 |
| convertible | 0.157 / 0.613 | 0.719 / 3.016 |
| big_ben | 0.262 / 0.950 | 0.848 / 2.655 |

Depth is the dominant error (0.3–0.6 mm of the median); meshing loses 0.1–0.26 mm median and up to about 0.95 mm p90 with perfect depth.

Meshing variants (object-only TSDF at 2× and 4× finer voxels, narrow or wide truncation, 0 or 5 smoothing passes; four scenes, perfect and real depth) found:

- The **truncation band width** decides it, not the voxel size. A narrow band (6 voxels) reproduces perfect depth precisely: jeep 0.085 / 0.361 to 0.038 / 0.117 mm.
- A wide band (0.12 map units, the current default) averages real depth noise. On real depth no variant beat the current settings reliably: jeep 0.340 / 1.250 current, 0.355–0.470 with a narrow band; big_ben improved but jeep, audi and convertible lost.
- Smoothing makes no measurable difference.
- The finest object-only volume raised coverage by 2–4 points (thin parts survive), at a cost in accuracy.

Defaults stay as they are. Revisit the narrow band once depth is more accurate. The harness used was a meshing-only rerun on kept dev runs (TSDF, then `surface.object`, then `surface.clean`, then `metrics.mesh`).

- The cause is the estimated focal: 1.0–1.5% short on the hard scans (−0.5% on scan24), which makes objects 1.4–1.9% too large relative to the camera rig.
- Tried without success:
  - exhaustive pairs (`PAIRS=exhaustive`): −1.51 to −1.43% on scan37, −1.36 to −1.03% on scan83;
  - estimating the principal point (`REFINE_PP=1`): slightly worse;
  - DA3's predicted focal: −2.1 to −4.0%, the same direction.
- DTU's arc of cameras leaves focal and object depth weakly separable from images. The truth-depth rungs of that run were invalid (fusion overwrote the injected depth); `stage_ranking.py` now runs them with `FUSION=`.

**The official metrics are now limited by placement, not shape.**
- Both official metrics place our mesh using a similarity fitted to our estimated camera centres. Published DTU methods use the true cameras, so they carry no placement error.
- On DTU the gap between official chamfer (0.889) and shape chamfer (0.515) is that placement error.
- The latest change improved shape chamfer on all 15 scans and the MobileBrick F-score on 16 of 18 scenes, but left both official numbers flat. Widening the TSDF band did not change that, so it's not a TSDF bias.
- To move the official numbers, improve camera placement and scale. Judge geometry by shape and F-score.

## Findings that shaped the design

- **Masks (2026-10-11):**
  - Lowering `VGGT_MASK_VOTE` to 0.6 only compensates for incomplete masks. With dataset masks: MobileBrick mean F@1 53.7 to 54.0 but shape p90 3.48 to 3.55; DTU chamfer 0.886 to 0.890. Kept at 0.8.
  - SAM-HQ refinement of tracker masks gains a little (jeep IoU 0.854 to 0.887); giving it more freedom (bigger box, wider band, looser overlap) made masks worse. CascadePSP changed nothing (0.853).
  - **BiRefNet with no prompt** scored IoU 0.86–0.97 on all 18 MobileBrick scenes and ≥0.985 on 11 of 15 DTU scans, beating a first-frame-prompted video tracker everywhere (the tracker failed outright on 6 MobileBrick scenes). Guided by tracker masks it gives the same masks where tracking holds.
  - Reconstructions from BiRefNet masks, both with the support filter (`runs/real/{mobilebrick,dtu}_sweep_birefnet_support/`; dataset-mask runs in `…_sweep_support/`): MobileBrick median F@1 / F@2 54.9 / 77.2 against 54.2 / 75.2, better on 12 scenes. DTU chamfer 0.868 against 0.863 mm on the 14 scans other than scan37.
  - Failures are about what "the object" is: DTU scan37 (tools masked, bricks not; chamfer 4.05 against 1.22) and big_ben close-ups (F@1 27.6 against 38.5).
  - The support filter is neutral with complete masks (≤0.2 F@1 per MobileBrick scene, ≤0.01 mm DTU chamfer) and removed big_ben's chair (shape p90 490 to 5.8 mm). Default since 2026-10-11.

- **Floaters in the scene mesh** come from surface seen by 1–2 frames. Hence `SCENE_MIN_VIEWS=3` and dropping pieces under 5%.
- **Focal:** the estimated focal is about 1.5% long on MobileBrick and within 0.5% on DTU (except scan37, 63 and 83, about 1.4% short). It changes overall size, not shape: shape after scaled alignment is identical with true and estimated focal. MobileBrick's reference poses and CAD meshes disagree slightly in scale, so the official metric includes a size term.
- **Depth error is mid-scale shape** (4–20 mm wavelength), shared across a model's views. Smooth correction fields recover at most about 40% even fitted to the truth (`bias.py`). Fine detail (high-pass) differs by only 0.1–0.3 mm between models.
- **VGGT and DA3** are equally accurate but err in different places. The best per-pixel pick of the six models would reach about 0.47 mm on jeep; the best per 16×16 block, about 0.52 (old vertex metric, against 0.65 for VGGT alone).
- **Agreement can't pick the right model,** because errors repeat across a model's views. Learned selectors on geometric and image cues didn't generalise. Pooled photometric evidence does.
- **Single-image models** (Depth Pro, Depth Anything V2, Marigold, and MoGe as a candidate) are worse than VGGT in every region type, despite their claims. The filter picks them for under 1% of pixels. Excluded from fusion.
- **Refinement needs wide baselines:** 10–35°, not the closest views. Slanted patches gave no measurable gain. Glossy surfaces (convertible) and 5 MobileBrick scenes lose some p90.

Four scenes remain unrun. **Conditioning as a learned error signal: proposed, built, measured, rejected (2026-10-14).** The idea was that a per-scene optimiser drives its objective to a minimum, so at convergence the objective's *value* is stationary and uninformative (which the photometric-confirmation experiment had already shown), while its *curvature* is not minimised and classical estimation puts the achievable error at about H^-1 sigma^2 - so uncertainty should come from the conditioning of the objective, not its residual. Features per pixel from depth, photos and cameras alone (no Gaussians, any depth source): the multi-view NCC cost sampled at relative depth offsets around the solution (value, curvature, asymmetry, best offset, margin to the next local minimum, span), the triangulation angles and view count, and the local depth spread. Labels: relative error against the reference mesh rendered per frame. Probe: leave-one-scene-out over the four dev scenes, gradient boosting, predicting error > 1%. The first-order half of the theory held - the residual alone scores AUC 0.583, barely above chance, and removing it from the full set costs nothing (0.794 against 0.795). The second-order half failed: **the whole signal is the local depth spread**, AUC 0.797 on its own against 0.795 for every feature together; the cost profile alone reaches 0.674 and adds nothing on top of roughness; triangulation geometry alone is at chance (0.493). Re-running with the offset range matched to the actual error scale (+-0.4% instead of +-2%, 13 points, since median error is 0.17-0.26%) changed nothing: 0.791 / 0.796 / 0.680 / 0.501. So error here is predictable zero-shot across scenes at AUC about 0.80, but from one trivial feature that edge-aware depth uncertainty has long used - not from the conditioning of the objective, and not a novel signal. Two things worth keeping: the stationarity argument explains the earlier confirmation failure rather than merely describing it, and the triangulation angles being at chance says the residual error on these scenes is not baseline-limited. Unseen surface / of that, symmetric: jeep 1.1% / 55%, big_ben 1.5% / 31%, convertible 2.2% / 54%, satellite 5.9% / 41%, colosseum 3.7% / 68% at full capture; at a 50% arc 16.8% / 37%, 4.3% / 36%, 16.5% / 34%, 13.9% / 34%, 19.2% / 66%; at 25% 29-45% unseen with 13-38% symmetric. **So on complete captures about 97% of the surface is already observed, and MobileBrick's official score excludes vertices outside the visibility volume, so completion of unobserved geometry earns nothing on the headline metrics.** It is substantial only for deliberately partial captures, and even there a single reflection supplies a third to two-thirds of what is missing, so a learned prior is left competing for roughly 10% of the surface at a 50% arc. Measured in minutes rather than after building a diffusion stage. **Towards watertight, lifelike scans (2026-10-15, jeep).** Audited against that goal rather than against chamfer, the current output falls short in three ways, and the biggest is not the one expected.

*Geometry is open.* The object mesh is not watertight, not edge- or vertex-manifold and self-intersecting: jeep 2,240 boundary edges in 15 loops (the largest holds 71% of them and winds across the whole object rather than capping the unseen base), big_ben 5,222 edges in 131 loops, 88 of them tiny. Neither off-the-shelf closure works: Open3D's `fill_holes` removes only 20% of the boundary even at a generous hole size (it handles small holes, not a 1,582-vertex rim), and screened Poisson on the oriented object points comes out **open too** (2,115 boundary edges at depth 9), because the cloud has no underside and the iso-surface clips at the volume boundary. The masks do work: carving a grid with every view's mask gives a visual hull that is 0 boundary edges, edge- and vertex-manifold, orientable and one component (jeep, 43 masks, 256-cube grid, 4 s). It only came out clean once the defects were fixed in the *grid* - largest connected blob, close one-voxel necks, slight blur before marching cubes - because repairing the mesh instead reopened it (`remove_non_manifold_edges` took the boundary from 9 edges to 20). What remains is self-intersection, which is why Open3D still reports `is_watertight()` false; the hull is also only a bound, so it is blocky and ignores concavities, and the next step is fusing it with the TSDF surface (accurate where depth was observed, hull where it was not).

*The visible defect is missing colour on surface we did photograph.* On-surface texels with no colour: 9.7% from 24 photos, 8.0% from all 43, against only 1.1% of the surface that no view observed at all. So the limit is the photos' usable coverage - grazing angles and occlusion - not the capture's.

*Splat renders fix that, and a composite keeps the sharpness.* The optimiser has already fitted a view-dependent radiance model to every photo, so it can be rendered from cameras that face the mesh head-on (`recon/surface/splat_views.py`: 32 even Fibonacci directions plus views aimed at normals the real cameras only ever see beyond about 70 degrees, written as frames plus a COLMAP model so `recon.surface.texture` consumes them unchanged; `gaussian_refine --export-gaussians` writes the 3DGS-layout PLY that `load_gaussians` reads back). Texturing from 33 renders instead of the photos: blank on-surface texels **8.0% -> 0.9%**, below the geometric limit, at a modest sharpness cost (Laplacian std 20.0 against the photos' 23.2). Compositing - photos wherever they have colour, renders only in the gaps, seam dilated by one texel - gives **0.7% blank at Laplacian std 24.5**, so better coverage *and* better sharpness than either alone, with 9.7% of the surface coloured from renders. Generative inpainting is therefore not needed for this: it is left for the roughly 1% that genuinely no view saw, where mirroring is the baseline to beat (see the headroom table). **Closing the object mesh (2026-10-15, jeep, `recon/surface/watertight.py`).** A staging error wasted most of this work and is worth recording: the pipeline's accuracy comes from the mask-vote extraction *after* the weighted TSDF, not from the TSDF itself - the raw weighted mesh (`work/object_tsdf.ply`, 105,080 faces) scores F@1 18.3 while the extracted mesh (`mesh/object.ply`, 54,835 faces) scores 75.7. A first attempt fused the hull into the TSDF field, upstream of that extraction, so it kept all the surface extraction removes; its F@1 of 13-18 alongside an official F1@2.5 of 85-88 was that, not imprecision, and four follow-ups (grid resolution, the hull clamp, localised blur, upsampling) were chasing an artefact. Close the finished mesh, not the field.

Closure methods, all scored on jeep (F@1 / shape median mm / official F1@2.5 / chamfer mm / boundary edges), against the open mesh's 75.7 / 0.372 / 90.1 / 2.85 / 2,240:
`fill_holes` closes 20% of the boundary (1,780 edges left) - it handles small holes, not the largest loop's 1,582-vertex winding rim; screened Poisson on the oriented points comes out open as well, 2,115 edges, the cloud having no underside; Poisson with hull points added where the mesh is missing reaches 69 edges but never closes, and costs accuracy (55.7 / 1.376 / 81.3 / 3.19); field re-fusion 61.5 / 0.913 / 88.5 / 2.46 / 0; **generalised winding number 66.7 / 0.678 / 87.7 / 2.64 / 0**; signed distance to the mesh 66.0 / 0.687 / 87.7 / 2.65 / 0.

The winding number (Jacobson et al., SIGGRAPH 2013; fast multipole form, Barill et al., SIGGRAPH 2018, through libigl 2.6.3, MPL-2.0) is the best of these and the one adopted: it consumes the finished mesh directly, is about 1 inside and 0 outside, and degrades gracefully where the surface is open because an opening subtracts only its own solid angle. Our meshes wind **inwards** (-0.685 at jeep's centroid), now probed and flipped automatically, and the interior magnitude of 0.685 rather than 1 is exactly that solid-angle deficit. The visual hull from the masks clamps the field so the closure cannot bulge out through the base: p90 falls from 16.6 mm (unclamped field fusion) to 5.7 mm.

**The remaining 2.4 points of official F1 are intrinsic, not a defect.** An object scanned from outside is an open shell; a watertight mesh must enclose a volume, so the shell is solidified - one sheet becomes two, separated by at least a voxel, displacing every point by about half a voxel (faces 54,835 -> 340,322). That is why doubling the grid changes nothing (87.7 -> 87.8), and why the winding indicator and a true signed distance score the same, which also refutes the half-voxel-localisation explanation tried first. Keeping both closure and the measured surface exactly would need the boundary loops capped with the original triangles untouched, rather than any level set. Defects are still kept out of the field rather than repaired in the mesh: `remove_non_manifold_edges` took the hull from 9 boundary edges to 20, and removing self-intersecting triangles then filling the holes oscillates (21 -> 19 -> 16 pairs while the boundary goes 0 -> 14 -> 24).

**Closure is robust topologically and not in accuracy, so the stage now refuses rather than guesses (five dev scenes).** Every scene closes cleanly - 0 boundary edges, edge- and vertex-manifold, orientable - but the accuracy cost ranges from mild to catastrophic. Open -> closed, F@1 and official F1@2.5: jeep 75.7/90.1 -> 66.0/87.7; audi 71.5/88.4 -> 56.6/86.4; big_ben 38.9/71.3 -> 33.4/67.5; satellite 45.8/68.1 -> 40.3/56.7; **convertible 45.8/55.4 -> 8.0/16.5**, its chamfer rising 6.7 -> 24.6 mm. The earlier claim that the cost is an intrinsic 2.4 points was measured on jeep alone and does not generalise.

The mechanism is the winding number's dependence on how open the input mesh is. Its interior value should be 1 for a closed surface; measured at the centroid it is 0.69 (audi), 0.69 (jeep), 0.51 (satellite), 0.42 (convertible), 0.14 (big_ben), and deep inside convertible it is **-0.233** - the sign is inverted over whole regions, so the output is a solid blob instead of a surface. This is the method, not the surrounding choices: convertible gives 16.5 from the plain indicator, from a true signed distance, with and without the hull clamp, and with depth-based free-space carving added (16.0). A scene-calibrated threshold raises the inside fraction (convertible 0.2% -> 44.7%) and changes the score by nothing, which is what finally identified the sign rather than the threshold as the fault.

Depth carving (`--depth-dir`, free space nearer than the measured surface, which silhouettes cannot carve) was added for concavities such as an open-top car's cockpit; it does not rescue convertible and costs jeep 4.8 points of official F1 (87.7 -> 82.9), so it is off by default.

**Two fixes made closure usable (2026-10-16): close the splat-refined mesh, and decide orientation from the interior.** The optimiser's mesh is more complete than the base one, which raises the winding number's interior value and so helps the very thing closure depends on. And the orientation probe was wrong: a single winding sample at the vertex centroid called big_ben positive while its interior is -0.690, so its field was inverted. Orientation is now decided from the median winding over the hull eroded away from its boundary, and the **faces** are flipped rather than the field, because `igl.signed_distance` takes its sign from the faces it is given - negating the field instead cost jeep 16 points of official F1 (89.0 -> 72.9), which is how that was caught.

This is a judgement rather than something the metrics settle: coverage prefers 300k, sharpness prefers 60k, and `ASSET_MAX_FACES` moves it either way.

*Texel density, not the fill, limits the textured asset.* The closed mesh carries far more faces than the open one (307,872 against 54,835), so at a fixed 4096 px atlas each face gets a fraction of the texels. Raising the atlas to 8192 px runs out of memory in `project_images_to_albedo` with 43 images; decimating instead (`--max-faces`) trades coverage for detail: 300k faces 1.36% blank, 100k 2.04%, 60k 2.13%. Photos paint 84.4% of the closed mesh's surface and the renders supply the rest, most of it the base no view saw.

One measurement to distrust: sharpness cannot be compared between two texture runs, because each re-unwraps the mesh independently and the atlases do not correspond texel for texel. Only within one atlas, or between runs of the same mesh with the same settings, is the comparison sound - which the earlier open-mesh table was. **Batched texture projection, so the atlas is a choice rather than a hardware limit (2026-10-24).** Open3D's `project_images_to_albedo` holds every image and the whole atlas at once, so 8192 px with 43 photos exhausted 23 GB and died. `texture.py` now projects in batches whose size scales with the atlas (`--projection-batch`, 0 = automatic), merging them by averaging wherever they overlap; memory is flat in the image count and 8192 px completes in 143 s across 5 batches. The first batch runs on the mesh itself so its material carries a real albedo map for the glTF writer, and the merge counts a texel as painted when it is not exactly zero - testing against the blank level instead dropped dim but genuine texels and cost a point of coverage. One batch reproduces the single call. Measured on the e2e jeep mesh at 4096 px, single call against batched: blank 2.55% against 3.48%, Laplacian sharpness 21.0 against 25.2 - batching is slightly less complete and noticeably sharper, because averaging fewer views per texel blurs less. Sharpness is not comparable between atlas sizes (different texel scale), so the 8192 figure of 20.9 says nothing against the 4096 ones.

**The camera ablation's fourth cell: the dataset's poses with intrinsics we estimate (2026-10-24, `runs/real/academic/dtu_posesonly.sh`, in progress).** The first scans are catastrophic - scan105 chamfer 7.471, scan106 7.528, against 0.886 for estimating both and 0.638 (scan105) for giving both - with pose error exactly 0.000 mm, as the poses are the dataset's, but size error 16.1% and 36.4% and shape chamfer (after scaled ICP) still 5.70 and 3.56. So **intrinsics and poses have to be consistent with each other**: estimating both lets the focal error and the pose scale co-adapt into a self-consistent reconstruction, while borrowing true poses alongside a mis-estimated focal grounds the depth at the wrong scale and distorts the surface. This also explains why true intrinsics alone buy so much (0.886 -> 0.594) while adding true poses buys almost nothing (-> 0.556): the focal is what the rest of the pipeline is calibrated against. **Mask quality: erosion is devastating, dilation is free (2026-10-24, `runs/real/academic/mask_sensitivity.sh`, jeep, depth held fixed and only the mask-dependent surface stages re-run).** Official F1@2.5 / chamfer against unmodified masks' 91.6 / 2.55: eroded 2 px **79.0 / 3.86**, 5 px 66.0 / 6.29, 10 px 32.2 / 18.57; dilated 2 px **91.8 / 2.46**, 5 px 91.2 / 2.52, 10 px 90.8 / 2.57; ragged boundary (+-4 px of smooth noise) 90.2 / 2.78. So a mask 2 px too tight costs 12.6 points while one 10 px too loose costs 0.8, and the shape median barely moves throughout (0.375 -> 0.354 eroded, 0.452 dilated): erosion does not distort the surface, it deletes it, which is why the coverage metrics collapse while the median error looks healthy. Masks should therefore be biased towards over-inclusion - the mask vote and the TSDF's own weighting discard surplus background, but nothing can recover surface a mask removed. **Adopted:** the automatic masks are grown by 2 px at a 960 px frame width, scaled to the real width (`recon.masks.birefnet --dilate`, `widen()`; `construct --mask-dilate`, `SCAN_MASK_DILATE`, 0 to disable). The gain itself is small (0.2 points); the reason to adopt it is the asymmetry, since the same 2 px in the other direction costs 12.6. It deliberately lowers the masks' own agreement with a reference matte, which is the quantity being traded for reconstruction coverage, so mask IoU is the wrong way to judge it.

**Tiled TSDF fusion works, and the ceiling moved rather than vanished (2026-10-24).** `--tiles` now derives its own box from the depth when none is given, so a plain large scene can tile; three bugs had to go first - a tile no frame reaches holds no blocks and extraction rejects that, valid-pixel counts were collected only from the first tile (which may reach nothing), and the report read `hashmap().size()` from a volume already released. Verified on jeep against the untiled mesh: 1, 8 and 27 tiles give 1.953 M / 1.946 M / 1.939 M faces and agree to within sampling noise (median distance 0.0167 against the 0.0169 self-comparison floor). On Barn it lifted the voxel from the memory-forced 27 mm to the 4.26 mm the benchmark's tau asks for (343 tiles, about 1.2 s each) - **but that is only worth F-score 5.29 -> 6.60** (recall 4.97 -> 8.19, precision 5.66 -> 5.53), against 2DGS's 36 and PGSR's 66, and it produced 207 M faces in a 6.8 GB PLY that took about 40 minutes to score. Two corrections follow: the earlier claim that Barn's score was the voxel rather than the depth was **wrong** - that held for Ignatius, while Barn is depth-limited; and tiling has to be paired with decimation or a voxel chosen for the output budget, since mesh size is now the binding constraint rather than fusion memory. **Saturation is a function of view count, and the boundary is measurable (2026-10-25, `runs/real/academic/view_count.sh`, jeep; cameras and object bounds from the full solve, so only the reconstruction is reduced).** Every attempt to feed the optimiser extra information failed at 43 views; the question was whether that is a property of the objective or of our dense captures. So the prior's value falls monotonically with view count and crosses zero between 4 and 8 views: **+10.5 points at 4 views, -0.6 at 8, -1.6 at 16, -3.0 at 43**. At 4 views the optimiser on its own is actively harmful (60.5 -> 52.0) - too few rays to constrain the surface it is free to move - and the prior is what makes it beat the base pipeline at all. This is the first of five attempts to add information to the objective that has worked, and it worked because the regime changed rather than the method.

**Confirmed on a second scene, where it changes the conclusion.** audi, official F1@2.5 base / optimiser alone / optimiser with the prior: 4 views 44.5 / 12.9 / 28.7; 8 views 81.3 / 40.1 / 72.4; 43 views 88.4 / 89.7 / 87.0. The trend is not only reproduced but stronger - the prior is worth +15.8 at 4 views and **+32.3 at 8** - and it still costs 2.7 at 43. But on audi the prior only *reduces* a collapse rather than winning: 28.7 and 72.4 both stay below the base pipeline's 44.5 and 81.3, where on jeep the prior did beat the base (62.5 against 60.5).

So the honest reading is not "priors make the optimiser win at few views" but **"the optimiser should not be used at few views at all"**: it degrades catastrophically there (audi 8 views, 81.3 -> 40.1 without the prior), and per-frame prediction followed by fusion is simply better. The prior mitigates the damage; it does not repair the regime. That points any sparse-view work at the feed-forward path rather than at per-scene optimisation, which is close to the opposite of where this would have gone on the jeep numbers alone.

The prior's benefit at 4 views is at least insensitive to its weight (jeep, official F1@2.5 against no-prior's 52.0 and base 60.5): weight 1 61.6, 3 62.5, 10 64.1, 30 62.4 - every weight from 1 to 30 gains 9.6 to 12.1 points, with a shallow optimum near 10. Two scenes, so the view-count trend is the robust part; the crossover point and whether the optimiser can ever win at few views are not.

Also added: `heldout split --keep N` keeps only N evenly spread frames, the inverse of the thinning split. Note the object's extraction bounds come from triangulated landmarks, which collapse with few views (4 views leave 4 points, 8 leave 44, 16 leave 181), so they are taken from the full solve alongside the cameras. **Why the base pipeline degrades at few views: information, not configuration (2026-10-25, `runs/real/academic/sparse_photometric.sh`).** Three candidate causes, all ruled out. The cross-view consistency check does not over-reject - it removes *less* at 4 views than at 43 (23.4% against 33.5%). Neighbours are still found (3 per frame at 4 views, 6 above), but at the wrong angles: the closest pair is 33 degrees apart and the median 117, against the 10-35 degree band the fusion filter and plane sweep select in, so patch matching is being asked to compare surfaces that look nothing alike. That predicts the photometric stages should hurt at few views, and on jeep at 8 views switching the fusion off indeed gained 4.1 points (73.2 -> 77.3, chamfer 7.92 -> 6.26) - **but audi reverses it** (81.3 with both against 80.6 without fusion, 80.4 without the sweep, and 65.8 with neither). Opposite signs on two scenes, so the hypothesis is not supported; the stages are about neutral at few views and removing both is clearly harmful.

So sparse-view degradation is a shortage of evidence rather than a mis-tuned stage, and it cannot be recovered by re-tuning what we have. Taken with the view-count curve, the practical position is that **our default multi-model fusion already is the right sparse-view method** - it beats the per-scene optimiser decisively below 16 views - and the open question is whether models can be combined better than by photometric scoring, which is exactly the signal the wide baselines make unreliable. That was tested next, and it closes the thread. `filter.py --combine {score,mean,median}` (default `score`, unchanged; `FUSION_ARGS`) replaces choosing between the candidates by pooled patch score with simply averaging them, which needs no photometric comparison. Official F1@2.5, score -> mean: jeep 4 views 60.5 -> 60.4, 8 views 73.2 -> **76.5**, 43 views 90.1 -> 89.5; audi 4 views 44.5 -> **45.9**, 8 views 81.3 -> 81.1, 43 views 88.4 -> 87.9. **Photometric selection wins at 43 views on both scenes (+0.6, +0.5) and is worth nothing at few views, where averaging is equal or slightly better** - the one large number, jeep at 8 views, is the same configuration that produced the unreplicated +4.1 from switching the fusion off, so it is scene-specific rather than a rule.

Taken together, three levers were tried against sparse-view degradation - the consistency thresholds, the photometric stages, and now the combination rule - and none recovers meaningful ground. The degradation is a shortage of evidence, and the default pipeline is already the best sparse-view configuration measured here. This is the second single-scene result in the thread to fail replication, which is why each was checked on two scenes. **How good is the photometric judge of the depth models? (2026-10-25, measured as the fusion actually runs.)** The fusion scores each candidate's depth by patch NCC against neighbours, pools over 17x17 blocks and takes the winner; `fusion_ceiling`'s block oracle says a perfect judge at that granularity would cut median depth error by 16-21%. Per block against the reference, the judge picks the better candidate **69.1% of the time on audi (605k blocks) and 64.8% on convertible (3.0M)**, against 50% for a coin. Mean pooled relative error - judge / oracle / averaging the two / always VGGT / always DA3: audi 0.0062 / 0.0054 / 0.0069 / 0.0073 / 0.0066; convertible 0.0107 / 0.0089 / 0.0116 / 0.0126 / 0.0106.

So the judge is genuinely informative, beats averaging by 6-8% and edges the better single model, and a perfect judge would gain a further 13-17%. That is a bounded target, and it corrects the earlier reading of the mesh-level result (+0.5 over averaging at 43 views) as the judge being weak: it is right two times in three, and the mesh is simply insensitive to the difference.

**This is also the one place in the project where a learned judge is not self-defeating.** The circularity result - that a signal derived from an objective is stationary at its optimum, measured twice - applies to judging a model *fitted* to the photos. The fusion's candidates are feed-forward predictions that never saw these photos as a loss, so photometric evidence about them is genuinely external, which the 69% confirms. Judging the models rather than the structure therefore remains open, and its mesh-level prize has now been measured by carrying a perfect judge through to the surface (`oracle_fuse.py`: per 17x17 block, the candidate actually closer to the reference). Official F1@2.5 / F@1 / shape median - the real judge's fused depth, the oracle's, and the pipeline's default (which refines the real judge's with the plane sweep): audi 86.5 / 63.8 / 0.541, 87.6 / 67.6 / 0.460, 88.4 / 71.5 / 0.411; convertible 52.7 / 41.0 / 0.880, 55.3 / 45.6 / 0.740, 55.4 / 45.8 / 0.745. So a perfect judge is worth 1.1 to 2.6 points over the real one, **but the plane sweep already recovers as much or more**, which is why the two had to be stacked. Oracle judge *plus* refinement against the default: audi 88.3 / 73.2 / 0.381, convertible 57.0 / 48.5 / 0.682.

**The ceiling on judge work is therefore about +2 points of F@1 and 7-8% of shape median, with nothing at the official 2.5 mm threshold on audi (88.3 against 88.4).** The gain is real but fine-scale: better selection buys depth precision, which shows at a 1 mm threshold and washes out at 2.5 mm. A learned judge capturing half the oracle gap would be worth about a point.

**Three ways to close that gap, all measured and all closed (2026-10-25).** *Its parameters are already near-optimal:* judge accuracy on audi at neighbours/radius/window/band/best-views 6/4/17/10-35/3 is 69.0%, against 68.2% with 12 neighbours, 63.6% with radius 8, 69.7% with a 5-60 degree band (no error improvement) and 64.8% with all three widened - bigger patches hurt most, so the signal is not short of evidence. *Hedging on its confidence does not work either:* picking beats averaging everywhere and monotonically (audi 0.0059 always-pick to 0.0066 always-average, convertible 0.0109 to 0.0118), so there is no uncertain region where averaging is the safer bet. *And a learned judge adds nothing:* with ten per-block features - both patch scores and their margin, inter-model disagreement, each model's depth roughness, image texture, view count, smallest view angle and depth - a gradient-boosted classifier trained leave-one-scene-out matches the patch score at best (accuracy 68.3 / 65.0 / 68.2 / 66.7% against 68.4 / 64.7 / 69.6 / 67.6%) and **the score margin alone has the higher AUC on three of the four scenes** (0.735 / 0.690 / 0.745 / 0.729 against the model's 0.726 / 0.700 / 0.731 / 0.695).

So the patch-score margin is a near-sufficient statistic for this decision given anything we can cheaply measure, and the residual 15-20% needs new information rather than a better reading of what is there - a different kind of evidence, or better candidate models. Judging the models is now closed on the same terms as judging the structure, though for a different reason: there the signal was depleted by the objective, here it is simply the best available. **Depth resolution: the first fine-accuracy gain of this phase (2026-10-25, `runs/real/academic/depth_resolution.sh`, `depth_res_mesh.sh`).** `DA3_RES` was 756 because that is where memory ran out with DA3's default window of 16 frames, not because it was measured. Memory is window x resolution, so a smaller window buys a higher one. The trade is visible: at 1008 halving the window again loses more than the resolution gains, and 1260/4 is worse than the default.

This is the clearest case in the project of the measure-on-dev, confirm-on-18 rule earning its keep: on four scenes the change looked like a straightforward adoption. **Fill for appearance, judge on evidence, label the difference (2026-10-26).** The best-scoring meshes do not pass an eye test, and an audit of them says why: it is not floaters or roughness (single connected component, 0% stray geometry, adjacent-normal disagreement 0.024-0.045 on every scene) but **holes and vertex colours** - 1,631 to 26,643 boundary edges, rendered as ~50k vertex colours rather than a texture. The two stages that fix exactly that, closure and splat texturing, both read as neutral or slightly negative on the benchmark, because the official metric is a 2.5 mm threshold that excludes everything outside the visibility volume. So the metric was discouraging the work that makes the output usable.

`texture.py` now records where every texel's colour came from: `--provenance-map` (default on) writes `<asset>_source.png` with 0 unpainted, 1 photographed, 2 mirrored, 3 rendered, the shares go into the asset's JSON, and the JSON carries a disclaimer that mirrored and rendered texels are inferred and accuracy should be judged on the photographed share. On a closed motorcycle asset: **82.1% photographed, 1.5% mirrored, 16.4% rendered**, with 0.14% left unpainted. Note MobileBrick's official score already restricts itself to the visibility volume, so the headline numbers were never inflated by the fill; it is this project's own shape metrics that do not restrict, which is part of why closure looked costly.

`--mirror-fill` (default off) fills unpainted texels from their mirror-symmetric partner's photographed colour before the renders are consulted, the axis chosen as the one whose reflection lands closest to the surface and only where it lands within 1% of the extent. **It is weak in practice: 1.5-2.0% of the texture on motorcycle**, against 16.4% from renders, and it costs sharpness (Laplacian 19.1 -> 11.4) where it does fill. That is far below the 31-68% of unseen *surface* with a mirror partner reported by the headroom table, because that asked only whether a partner exists, not whether the partner was photographed and the reflection lands on real surface - and a motorcycle is much less symmetric than a car. **That first reading was wrong, through a bug of mine.** `texel_points` flipped v when rasterising the UV triangles, so every texel was given its vertical mirror's surface point: checked against ray-cast surface points, median position error 0.81 map units flipped against **0.0003 unflipped**. The mirror fill was therefore copying colour from the wrong place. Corrected, symmetry supplies **6.3% of the texture rather than 1.5%**, and the synthetic render share falls from 16.4% to **10.5%**. A test now pins the convention by asserting each texel's point directly.

Mirrored colour is real photographed colour, but it is spatially coarse: sharpness is 12.64 against 19.11 for renders alone (11.35 before the fix), because the nearest-neighbour lookup maps many target texels onto one source and leaves flat patches. So the choice between the two fills is real colour smeared against synthetic colour sharp, `--mirror-fill` stays off by default, and about **10.5% of the asset is still plausible interpolation with no observation behind it** - the honest target for a generative prior, now labelled rather than silently blended in.

**The judge for that is built (`recon/evaluation/diagnostics/unseen_colour.py`).** Views are held back from the texturing; each held-out camera is ray-cast against the mesh, the hit's barycentric coordinates give its texel, and the asset's colour there is compared with the photograph, split by provenance. It is validated: on views the texture *was* built from, mean absolute colour error is 21.7 of 255 - consistent with averaging twelve views against one photograph - and settling that number is what exposed the v-flip, since the wrong convention read 48.7. Any generative filling can be scored the same way against the same photographs. Holding out every third frame leaves too little inferred surface to test (11k pixels against 491k photographed), so the protocol holds back a contiguous arc instead (`heldout split --arc LOW HIGH`, the inverse of thinning).

**Run on motorcycle, and it largely answers the question (2026-10-26).** Frames 0-25 kept, 26-64 held out; the Gaussians were refitted on the arc alone, so the renders carry no information about the far side, and the texture used only the arc's photographs. Geometry came from the full-view closed mesh - the arc's own mesh is too open for the closure to accept (interior winding 0.340, correctly refused) - so this measures inferred *colour*, not inferred shape. Mean / median absolute colour error out of 255 against the held-out photographs, over 176k inferred pixels: **renders 31.7 / 23.0 against 26.8 / 19.7 on photographed surface**; with mirroring on, mirrored texels score 39.9 / 24.3, rendered 32.8 / 21.3, photographed 30.9 / 20.7.

So **the splat renders fill unobserved surface nearly as accurately as observation itself** - about five points of mean colour error between inferred and photographed - and mirroring is the worse filler, now against real photographs rather than inferred from symmetry statistics. That bounds what a generative prior could win here at roughly those five points, on about a tenth of the asset, and it would have to beat an extrapolated radiance field that is already close to observation quality. It also explains why the closed, textured asset looks acceptable: the fill is genuinely good. **And the shape half, measured the same way (`recon/evaluation/diagnostics/unseen_shape.py`).** The arc protocol cannot reach inferred shape - an arc leaves the mesh too open for the closure to accept - but the datasets ship complete ground truth, so the reference surface can be sampled, marked observed or not exactly as the capture-headroom diagnostic does, and compared against our mesh. Median / p90 distance from reference samples to our surface, observed against unobserved: motorcycle open mesh 1.03 / 2.40 against **2.83 / 5.32**, closed 1.05 / 2.50 against **2.17 / 4.73**; jeep open 0.63 / 3.24 against **3.24 / 8.42**, closed 0.78 / 3.32 against **2.26 / 6.42**.

So unobserved shape is **two to three times worse than observed**, a proportionally larger gap than colour's 1.2x, but it covers only 1.1-2.4% of the surface - and the hull **improves** it rather than merely filling it (2.83 -> 2.17 mm on motorcycle, 3.24 -> 2.26 on jeep), while costing a little where the views did look (1.03 -> 1.05, 0.63 -> 0.78), which is the closure's known price.

Taken together the two halves bound generative completion from both sides: about five points of colour error on a tenth of the asset, and about a millimetre of shape error on a fortieth of it, against fills that are already closer to observation than expected. Diffusion is therefore not the obvious next step it appeared to be, and both measurements are cheap and repeatable. **Appearance as numbers (`recon/evaluation/diagnostics/appearance.py`).** The quantities that decide how an asset looks were being computed by hand, which is why the gap between the benchmark and the eye went unnoticed for so long. The diagnostic reports them together and needs no ground truth, so it runs on any capture: boundary edges and whether the surface is closed, manifold and orientable; connected pieces and the share of triangles outside the largest; roughness as the mean disagreement between adjacent face normals; the share of on-surface texels with no colour and the sharpness where they have it; and the provenance shares. On the closed motorcycle asset: closed, manifold, orientable, one piece, no strays, roughness 0.011, 1.59% of the surface blank, sharpness 22.2.

One trap it now avoids: read from a textured `.glb`, the topology looks shattered - 22,302 boundary edges, 849 pieces, 96% "stray" - because UV unwrapping splits vertices along chart seams. Those are not holes. Topology is read from the untextured mesh beside the asset, and the report says which file each half came from. **Extraction thresholds swept, and nothing worth adopting (2026-10-26, `runs/real/academic/extraction_sweep.sh`).** The mask-vote extraction carries the pipeline's accuracy, yet its thresholds had never been measured; the sweep re-runs only that stage and the scoring on the existing TSDF mesh, so depth and fusion are held fixed. Mean official F1@2.5 over the four development scenes, against the default's 77.47: mask vote 0.6 **77.70**, 0.7 77.67, 0.9 **75.92**; component support 0.1 and 0.4 both 77.47; min-views 3 77.45. A looser vote is worth +0.2 and a tighter one costs 1.6, which matches the mask asymmetry - over-inclusion is cheap, over-tightness expensive - but +0.2 is well inside the margin that failed to generalise today, so the default stays at 0.8.

`--min-component-support` not moving the score across a fourfold range is not an inert knob: these objects extract as a **single** component above the 1000-face floor, so the weak-support test compares that component's mask count against its own and can never drop anything. It is there for a capture where the segmenter takes a chair for the object in a few frames, which the development scenes do not contain.

**DA3's window sized to the card, and what the OOM warnings in the logs actually are (2026-10-26, `recon/depth/multiview/da3.py`).** The stage's window was a fixed 16 frames, chosen for this machine's 25 GiB card, so the pipeline could not run on a smaller GPU without being retuned by hand. Peak allocation of one window, measured on 1600x1200 input at `--process-res 756` (DA3-Giant, whose weights are 5.11 GiB of it): 7.89 GiB at 3 frames, 8.81 at 4, 12.49 at 8, 13.33 at 12, 14.21 at 16, 15.93 at 24. Beyond eight frames the curve is **linear, not quadratic** - DA3 does not attend over all views at once - and the activations fit 5.66 GiB + 0.215 GiB per frame, scaled by the square of the processing resolution. `--window auto` (the default) takes the largest window fitting 90% of the memory free after loading, capped at `--max-window 16`; a window that still will not fit is halved rather than abandoned. Floor of 3: DA3 aligns its poses to ours by Umeyama, which raises `Degenerate covariance rank` below three camera centres.

On this card auto chooses 16 from 15.2 GiB free and the depth is **bit-identical** to the fixed window (max absolute difference 0.0 over 64 frames of scan105, same median fit scale 1.031194), so no published result moves. At `DA3_RES=1008` the model picks 9 where the earlier measurement hand-chose 8, which is an independent check on it. A 12 GiB card gets 4 frames; the sizing is `fitting_window`, tested in `tests/depth/test_da3_window.py` without a GPU.

This also corrects two claims. The `memory allocation failed with OOM` warnings in the logs are **not** a ceiling being hit: they appear in 114 run logs across every dataset, MobileBrick asking for larger blocks (3.12 GB with 1.94 GB free on jeep) than DTU did, and they are the caching allocator releasing cached blocks and retrying - window 16 at 756 peaks at 14.21 GiB of 25. And the Makefile's note that 756 with a window of 16 "is simply where memory ran out" was wrong for the same reason; what ran out was 1008 *with* that window, which is why that measurement halved it.

**How many captures the closure refuses, and why the old per-scene figures were wrong (2026-10-26).** The gate's own comments carried interior winding values from the closure's development - 0.69 audi and jeep, 0.51 satellite, 0.42 convertible, 0.14 big_ben - and those meshes predate the planar-Gaussian optimiser. Measured again on all 18 scenes of the current pipeline (`runs/real/refine_mb/<scene>/pgsrform`, by running the closure with `--require-interior 1.1` so it reports and writes nothing): castle 0.230, bridge 0.232, convertible 0.236, boat 0.289, colosseum 0.333, ferrari 0.392, porsche 0.432, audi 0.577, satellite 0.595, beetles 0.603, aston 0.631, jeep 0.647, camera 0.667, space_shuttle 0.680, big_ben 0.771, motorcycle 0.783, london_bus 0.832, cabin 0.848. **Seven of 18 fall below the 0.5 gate and eleven close.** big_ben moved from the worst mesh (0.14) to the fourth best (0.771), so the optimiser closed it substantially; audi and jeep came *down* from 0.69. The stale figures are corrected in the module.

Two explanations for the seven were tested and neither holds. **Camera coverage is not it**: MobileBrick orbits every object, and DTU's hemispherical rig scores 0.411 - higher than seven MobileBrick scenes. **Openness is not it either**: interior winding against boundary edges correlates only -0.44, and against boundary edges per unit root-area -0.39; satellite passes at 0.595 with 7,593 boundary edges while ferrari is refused at 0.392 with 1,597.

What the seven have in common is that they are the least convex - a castle with courtyards, a colosseum's ring, a bridge's arches, an open-topped convertible, boat and sports cars - and the probe is the **visual hull eroded away from its boundary**, which assumes the object fills its hull. For these objects the eroded hull lands in courtyards and cabins: inside the hull, outside the surface, where the winding number is correctly near zero. So the gate partly measures convexity rather than the field's usability.

**Probing the enclosed volume instead does not fix it (rejected, code removed).** Replacing the erosion with a flood fill of free space inward from the grid boundary - so that what the flood cannot reach is genuinely surrounded by the surface - finds *nothing* enclosed in these meshes: with 1,600 to 26,500 boundary edges, free space leaks in through the holes everywhere. On castle, jeep, audi and big_ben it fell back to the erosion and reproduced it exactly; on convertible and colosseum it left the interior unmeasurable. A probe cannot find an enclosed interior in a mesh that has none, so a better interior measurement is the wrong place to attack this.

**One real bug it exposed, fixed.** An unmeasurable interior passed the gate: `interior` is NaN when there are too few deep voxels to take a median over, and `interior == interior` is then False, so the refusal was skipped and the mesh closed anyway - in exactly the case where the blob is most likely. The gate is now `not interior >= a.require_interior`, which refuses on NaN and says so. jeep still closes and convertible is still refused at 0.236.

**The Tanks and Temples scores are invalid: every scored mesh was built coarser than the benchmark's own tolerance (2026-10-26).** Scene support is a second mode beside object scanning, so the scene path's state was measured properly. Our scores against PGSR's published figures looked like a widening failure with scene extent - Ignatius 48.7 against 80, Truck 27.6 against 60, Barn 6.6 against 66 - and the cause is the meshing voxel, not the reconstruction. The official scorer matches a point when it lies within tau of the other cloud, so the voxel must be at most tau/2 in map units, which `runs/real/academic/tnt.sh` computes from each scene's scale. Measured back from the median triangle edge of the mesh that was actually scored, against the voxel that scene required: Ignatius 0.00402 against 0.00175 (**2.3x too coarse**, 0.34 cm against tau 0.3 cm), Truck 0.01215 against 0.00392 (**3.1x**, 0.77 cm against 0.5 cm), Barn 0.02162 against 0.00426 (**5.1x**, 2.54 cm against 1.0 cm). The coarseness ranks exactly with the gap: Barn's triangles are two and a half times the distance at which a point counts as matched, so its precision and recall sit near 6% from four different pipeline variants, which is the signature of quantisation rather than of error.

The script asked for the right voxel (`--voxel tau/2 --bounds --tiles 0`) and `runs/real/academic/barn_tiled.log` shows that build finishing - 410 frames, 207,264,432 faces, 343 tiles of 7.6 GiB - but `mesh/scene.json` for Barn records `source_faces: 6,790,787`, so the fine mesh never reached the cleanup or the scorer. That matches the known corruption from editing `tnt.sh` while it was running. **No conclusion about scene-mode quality can be drawn from the current numbers**; the meshes must be rebuilt at the benchmark voxel and rescored first. The 3% of Barn's intended faces that were scored is also why its `kept_components` of 3 looked benign.

**Scene-first reconstruction with 3D segmentation beats the masked object pipeline (2026-10-26, jeep, `runs/real/scenefirst/`).** The architecture was inverted at the user's suggestion: reconstruct the whole scene with **no masks anywhere**, so the image-based judges see full frames, then extract the object in 3D afterwards. The motivation is in the mask-sensitivity result - eroding a mask 2 px costs 12.6 points while dilating it 10 px costs 0.8, because "erosion does not distort the surface, it deletes it" - whose limit is no mask at all. Every stage (depth, fusion, 3 refinement passes, the cross-view check, the planar-Gaussian optimiser, the TSDF) ran on a jeep sequence whose masks were replaced by solid white, with `OBJECT_TSDF=scene`, fusing the table too: 2,867,777 faces.

Three cuts of that one mesh, scored against the same reference (official F1@2.5 / precision / recall / chamfer mm / F@1 / F@2 / shape median mm):
- object-first, the current default, masks driving every stage: **92.72** / 98.03 / 87.96 / 2.69 / 82.30 / 91.20 / 0.256
- scene-first, cut by the masks' visual hull at the pipeline's own 0.8 vote: 85.83 / 98.27 / 76.19 / 3.47 / 74.71 / 84.58 / 0.254
- scene-first, cut by learned per-Gaussian labels: **93.43** / 97.90 / **89.35** / **2.42** / **83.61** / **92.43** / **0.250**

**Unmasked reconstruction is not worse but marginally better**: the hull arm already matched the baseline's shape median (0.254 against 0.256) and beat its precision (98.27 against 98.03) while losing 11.8 points of *recall*, which is missing surface rather than wrong surface - the mask-erosion signature again, now coming from the extraction instead of the mask. The visual hull is **occlusion-blind**: it intersects silhouette cones, so it cannot distinguish a surfel on the table from one under the object. Learning the label recovers 7.6 of those points and ends 0.71 above the masked baseline on the official score, with 3.3% of 938,971 Gaussians labelled foreground.

**How the label works (`recon/depth/gaussian_refine.py`).** One foreground logit per Gaussian, alpha-composited like colour through the same 2DGS rasteriser (`render_labels`, `sh_degree=None`) and trained by binary cross-entropy against the 2D masks wherever the render has coverage (`--labels`, `--label-weight .5` from iteration 500, `--export-labels`). This is the identity-feature idea of Gaussian Grouping (Ye et al. 2024) and SAGA (Cen et al. 2023), implemented here rather than ported. Two properties matter: the render **detaches means, quats, scales and opacities**, so no mask can move a surfel and the geometry is exactly what it would be without any label; and every view votes, so a mask that eats part of the object in one frame is outvoted rather than deleting that surface. Rasterisation decides which Gaussian a pixel sees, so a table surfel is supervised as background in the views that see it while an occluded one simply receives no gradient. The mesh is then cut per vertex by an inverse-distance-weighted average of its eight nearest Gaussians' probabilities.

**A latent bug this exposed:** `rebuild()` carries Gaussians through densification by zipping the optimiser's param groups against the hardcoded `NAMES` tuple, so a parameter absent from it keeps its old length while the Gaussian count grows, and the rasteriser then rejects it. Any future parameter must be added to `NAMES`; a comment there says so.

**Not yet adopted.** This is one development scene, the margin on the official score is 0.71, and margins of that size have failed to generalise here before; audi, convertible and big_ben come next, then the other 14. Two implementation debts if it is adopted: the labels came from a second optimiser fit applied to the first fit's mesh by nearest neighbour, where one fit should produce both (and halve the cost), and the scene-first arm is heavier throughout - a 2.87M-face TSDF and 939k Gaussians against the object path's 53k-face mesh. The experiment's own scripts are still outside the repository.

**Where unmasked reconstruction loses thin surface, located exactly: the depth grounding, not the segmentation (2026-10-26).** Scene-first was confirmed on all four development scenes against a **same-day masked control** (the 2026-10-14 baselines were only 0.18 behind today's code on jeep, so the vintage was not the explanation): official F1@2.5 jeep +0.53, audi ~+0.40, convertible ~+0.51, big_ben ~-0.15, mean about +0.32, while the **net F@1 change over the four is zero**. The label fit itself is stable - refitting with a different seed moves official by 0.05 - so the spread is not noise.

big_ben is the scene that loses: F@1 51.18 -> 46.99, precision@1 75.22 -> 70.78, recall@1 38.78 -> 35.17, shape median 0.528 -> 0.585, with 4% less surface area (47.07 against 49.05 units squared). Three candidate causes were ruled out by measurement. **Not the segmentation**: six cut variants (1, 2, 4 and 8 nearest Gaussians; thresholds 0.5 and 0.7) all land between 46.6 and 47.0, a spread of 0.4 against a 4.2 deficit. **Not vertex smoothing**: the unsmoothed k=1 cut scores 46.74, no better than the 8-neighbour average. **Not resolution**: the scene-first mesh is slightly *finer* (median triangle edge 0.01936 against 0.02018).

It is the **grounding**. `recon/depth/grounding.ground` fits one global affine (scale and shift) per frame to the sparse anchors that `object_anchors` selects **through the mask**, so white masks draw anchors from the whole scene. On a matched same-day pair of jeep runs the DA3 stage's fit degrades from median relative anchor error 0.0057 (p90 0.0079) to **0.0139 (p90 0.0223)**, a factor of 2.4, and the fitted scale moves 7.5% (1.0219 -> 1.0971); p90 approaches the 0.03 rejection threshold. Per-pixel depth error on big_ben's object pixels is worse at every stage - VGGT 4.67, DA3 3.89, fused 3.27, refined 2.56 mm against the recorded masked 3.88 / 2.95 / 2.77 / 2.16 - even though the depth models read untouched photos either way and cannot see a mask. This also explains the pattern: jeep, audi and convertible are compact and dominate their own depth range, while big_ben is a tall tower spanning a large range with a table around it.

**Region-wise grounding fixes the fit and changes nothing on the mesh (2026-10-26, rejected for objects, `recon/depth/grounding.fit_regionwise`, `GROUNDING_REGIONS`, default 1 = the global fit).** Since monocular depth is only locally affine, the anchors were clustered in position *and* predicted depth together, fitted per cluster by the same robust routine, and blended per pixel with a Gaussian kernel half the typical centre spacing wide. On a synthetic frame holding two different affines it fits them exactly (anchor error 0.00000 against the global fit's 0.102 at four or more regions). On the four development scenes at eight regions it does what it was built to do and nothing else - median relative anchor error jeep 0.0139 -> 0.0049, audi 0.0160 -> 0.0060, convertible 0.0076 -> 0.0031, big_ben 0.0042 -> 0.0025, a 40 to 65% improvement - while official F1@2.5 moves -0.16 / +0.06 / +0.13 / -0.23 (net about -0.05, inside the noise) and F@1 -0.21 / -0.10 / -0.45 / -0.39 net negative. **big_ben, the scene it was built for, got slightly worse.** So the grounding error is a symptom that tracks the mask change, not the cause of the lost surface: a better affine fit does not make a better surface. It also costs 77 ms a frame against the global fit's 4 (after an optimisation from 212 ms; four and eight regions cost the same, so the cost is per-pixel traffic, not per-region work), which is about 7% of a scene's pipeline time for no measurable gain.

Kept behind a default-off flag for one reason only: Tanks and Temples has a far wider depth range than any object and has never been tried with it, and that is the one place the mechanism should matter. If it fails there too the code should be removed by the same rule that removed the other rejected experiments. **Three hypotheses for big_ben's deficit are now ruled out by measurement - the segmentation, the meshing resolution and the grounding - and no fourth is offered here.**

Two remedies remain untried: a two-pass scheme that grounds globally, segments in 3D, then re-grounds on the object's own anchors, using the segmentation as an attention mechanism; or keeping masks for grounding alone, which is not a new dependency since the 3D labels already need them but forfeits the unification.

**Segmentation survey for the 3D cut (2026-10-26).** Part segmenters of an isolated mesh (P3-SAM, SAMesh, GeoSAM2) solve a different problem. Indoor instance segmenters (SpaCeFormer 2026, Open3DIS, UniC-Lift, MaskClustering) are trained on ScanNet/Replica and would discard our masks. The two that fit are **FlashSplat** (ECCV 2024): the rendered 2D mask is linear in the per-Gaussian labels, so the optimal assignment has a closed form solved in one step, about 30 s, under the research-only Gaussian-Splatting licence, formulation simple enough to reimplement; and **Trace3D** (ICCV 2025, Apache-2.0), whose per-view instance weight matrix corrects inconsistent masks, which is not our bottleneck since MobileBrick's masks are clean. GaussianCut's graph cut adds a smoothness term, which is the wrong tool for small parts. None of them addresses the grounding above, so none would recover big_ben.

**The 3D cut solved in closed form on the existing fit: same accuracy, seconds instead of a second optimiser pass (2026-10-26, `gaussian_refine.solve_labels`).** FlashSplat's formulation (Shen et al., ECCV 2024) is reimplemented without its research-only code: the rendered mask is linear in the per-Gaussian labels, so the optimal binary assignment decouples, and a Gaussian is foreground when its alpha-blending weight accumulated over mask pixels exceeds its weight over background pixels times `--label-bias`. No change to the rasteriser is needed - rendering R = sum_i w_i l_i makes dR/dl_i exactly the blending weight, so one backward pass of sum (mask - bias (1 - mask)) R per view yields the whole decision statistic; the sigmoid on the labels scales each Gaussian's gradient by a positive constant and cannot change its sign, so `render_labels` is reused as is.

Run first inside a second optimiser fit (`--label-solver closed-form --label-weight 0`), it matched the cross-entropy head on official F1@2.5 - jeep 93.43 -> 93.46, big_ben 77.88 -> 77.96, convertible 61.39 -> 61.93, audi 90.27 -> 90.28 - but took the same ~90 s, because the cross-entropy loss was already riding on the geometry fit almost for free. **The saving only appears on Gaussians that are already fitted**, which is how FlashSplat is meant to be used and which `make refine-gaussian` already produces. Two things made that work. `load_gaussians` bypasses `__init__`, so it never created the label logit, and now does. And it returns the 3D-Gaussian class while the export is 2DGS surfels, but `render_labels` is inherited and rasterises through the 2DGS path, which ignores the third axis: rendered back from the PLY, the depth matches what the fit itself exported to a median relative difference of 5.6-7.7e-4 (p99 0.6-2%) with full coverage over five frames, two orders below any effect measured here.

Solved directly on each run's `depth/gaussian/gaussians.ply`, with no second fit: **load 1.2-2.5 s and solve 0.7-1.4 s** against about 90 s for the fit it replaces, and the labels now sit on the same Gaussians that produced the mesh, which removes the nearest-neighbour transfer between two different fits. Official F1@2.5 against the cross-entropy head: jeep 93.43 -> 93.41, big_ben 77.88 -> 77.74, audi 90.27 -> 90.31, convertible 61.39 -> **62.20** (F@1 55.71 -> 57.35) - parity within the 0.05 seed noise on three scenes and a gain on the fourth, so it is the better way to make the cut even at a tie. **Why scene-first loses on validation: the comparison changed the fusion as well as the masks (2026-10-27).** The overnight scene-first arm ran with `OBJECT_TSDF=scene`, so it removed the masks *and* replaced the weighted object TSDF (VGGT-DA3 agreement and angle weights, a 3-view minimum, two robust passes) with the plain scene TSDF. That second change has been measured on its own, with masks held fixed (2026-10-12, above): the scene TSDF loses F@1 by 1.8-5.6 on the development scenes with a similar p90. That is the same metric, size and signature as the validation deficit - 1 mm worse, 2.5 mm flat - so the overnight result does not isolate the masks.

What the losses are, on the 17 non-spent scenes. Poses are identical between arms (one COLMAP solve), face counts match, and scene-first's scale error is *smaller* on most scenes, so none of those explains it. Precision losses are partly clutter: surface more than 2 mm from the reference grows from 14.1% to 24.9% on colosseum and 22.5% to 28.7% on castle. Diffing the two meshes in their shared frame, the surface scene-first adds lies outside the object's footprint for 33% of ferrari's and 23% of castle's, and below the base for 12% of aston's - table or baseplate the 3D cut keeps. Recall losses are not localised: motorcycle and camera differ from the masked mesh over about 20% of their surface, a depth difference rather than a cut. The grounding-contamination explanation is not supported. The share of a frame's anchors that lie on the object does not predict the F@1 change (Spearman -0.10, p 0.70): camera and jeep have the fewest object anchors (2.0%, 3.9%) and both gain. The share of the frame's depth range the object spans does predict the shape change (+0.54, p 0.02): castle 98%, big_ben 65%, bridge 57% and colosseum 46% all lose.

Why the arm switched TSDFs at all, since nothing in the weighting depends on masks: the weighted TSDF is a **dense** grid over the box of the sequence's landmarks, and those landmarks are exported through the sequence's masks. With white masks the box becomes the whole table - jeep 1.4 M -> 514 M voxels (about 11.5 GiB of state), big_ben 24 M -> 943 M (about 21 GiB before the coordinate tensor), colosseum 6.6 M -> 238 M - which does not fit the card, while the scene TSDF is a sparse hashed grid that does. The switch was a memory workaround, and it cost the weighting with it. `WEIGHTED_LANDMARKS` (default `$(LANDMARKS)`) now separates the grid's box from the sequence: pointed at landmarks exported through the real masks, it keeps the box object-sized (jeep 645 landmarks, the same as the masked arm) while every pixel of unmasked depth inside it is fused. The masks then bound the grid and supervise the 3D cut, and delete nothing. That is the one-variable test (`runs/real/academic/scenefirst_weighted.sh`, `runs/real/scenefirst_weighted/`): the overnight scene-first run copied, only the weighted TSDF, extraction and the cut rebuilt, and scored against the overnight masked control. **VGGT-Diff as a generator of unseen views: it follows the requested camera only near real photos (2026-10-27).** VGGT-Diff (Chen et al. 2026; Wan2.1-I2V-14B with VGGT-Omega conditioning; VGGT-Diff Research License, non-commercial; `third_party/VGGT-Diff`, venv `~/.venvs/me566-vggtdiff`, weights `runs/models/vggtdiff`) generates images at requested cameras from six source photos. It is the candidate generator for the user's intended self-building loop, in which synthetic views fill unseen surface and are gated against well-observed surface, never against themselves. Test: the motorcycle held-out arc (frames 0-25 kept, 26-64 never seen, from `runs/real/pgsr_mb/motorcycle/ours`), six sources spread over the kept arc, ten held-out targets, scored inside the object mask against the real photographs on the same 832x480 cover-crop the model uses. The splat renders come from that arc run's Gaussians, which never saw the targets.

Two defects in the released inference code had to be worked around without editing it. `VGGTDiff` hardcodes the trajectory family (it validates for the temporal Plucker adapter and configures the DiT as `trajectory`), so the NVS checkpoint the README pairs with independent views fails to load. And `generate` passes `num_latent_frames=None`, which the pipeline then derives with the video VAE's 4x temporal compression, where NVS has one latent per view - its own training sets sources + targets (`vggtdiff/training.py`).

Mean over ten targets: generated PSNR 12.82 / MAE 42.7 / SSIM 0.174, splat 18.14 / 23.3 / 0.569; splat wins on every target. Registering each generated image to the real photograph (SIFT, RANSAC similarity) separates a pose problem from an appearance problem. Within 31 degrees of the nearest source (frames 26, 28, 33) the generated view matches the real camera - scale 1.01-1.04, shift 2-8 px, under 1 degree of rotation, 122-1388 inliers - so the camera handling is right. Beyond about 35 degrees (frames 38-64, 34-56 degrees out) only 3-5 matches survive: the model draws a plausible scene from a different viewpoint. It holds the camera only where the photographs already constrain the surface and our splat renders are sharper (PSNR 27.4 against 15.4 at frame 26), and it drifts exactly where the unseen surface is. Cost: 65 s per view at 50 steps plus 86 s to load, 8.1 GiB peak with CPU offloading. Untried: the trajectory checkpoint, which generates a contiguous path in one pass from real sources and may hold pose further out than isolated jumps. The harness (`generated_views.py`, `vggtdiff_nvs.py`) is still in scratch and comes into the repository if the loop goes ahead.

*Re-posing does not rescue the far views.* A view drawn from the wrong camera would still be usable if its true camera could be recovered, so each generated image was registered to the real photographs: SIFT matches against the 26 kept frames, matched real pixels back-projected through their consistent depth, PnP with RANSAC. The near views register at their requested cameras: 11,440 of 15,310 matches at frame 26 and 13,129 of 17,427 at frame 28, within 0.08 orbit radii and 1.2-1.6 degrees of the true held-out camera, and 938 of 2,129 at frame 33 (0.10, 2.1 degrees). The far views do not register from any camera: 7-21 inliers of 650-1,300 matches (1-3%), and the three PnP solutions that nominally pass are noise, 73-178 degrees off. Even the rug, which the real photographs show all the way round, fails to match, so the model invents the background as well as the object's far side. These images are not views of this scene, mislabelled or otherwise. The registration does give the loop its gate: 44-75% inliers for coherent views against 1-3% for invented ones, a margin wide enough to need no tuning, at seconds per view. Every view that passes it lies within about 30 degrees of a real photograph.

*The trajectory checkpoint, placed by our own pose solver, extends the scene into the gap (2026-10-27).* The user's point: the pipeline already solves poses from images alone, so generated frames do not need to land at the cameras they were requested at - solve them jointly with the real photos and let coherent ones attach. The trajectory checkpoint (`VGGT-Diff-Trajectory-480x832`, 32.8 GB; the released `infer.py`) generated 80 contiguous frames walking the true camera path from frame 25, the edge of the kept arc, to 64, in half-frame steps, conditioned on the same six real photos. That took 1,305 s including the model load, and 56 GB of host RAM with CPU offloading. The 26 real frames, cover-cropped to the same 832x480 and so sharing one camera, and the 80 generated frames then went through `recon.cameras.solve` with exhaustive pairs: **105 of 106 registered into one model** (79 of 80 generated). After a similarity fit to the full solve on the real frames (median residual 0.0074 orbit radii), placement against the true held-out cameras falls into three zones: frames 25-37 within 0.1-0.3 orbit radii and 1-4 degrees; frames 38-47 at 0.2-0.7 radii and 4-15 degrees; frames 48-64 at 1-2.7 radii and 72-174 degrees. Measured as azimuth round the object, the real kept arc covers about 200 -> 360 -> 23 degrees and the gap is 27-199. The registered generated cameras advance from 23 to about 104 degrees, then stall between 111 and 133 looking at the object. So the synthetic path covers about 110 of the gap's 172 degrees, all of it accepted by the solver as consistent with the real photos and with itself.

Fidelity where it can be checked against the held-out photographs: after aligning each generated frame to its real photo by feature homography, frames 26-36 (37-347 inliers) score PSNR 13.0-16.3 and mean error 25-39 against our splat renders' 19.0-27.4 and 7-19. From frame 38 on, only 4-6 features match the real photo, so the content there is invented rather than reconstructed - expected for surface nobody photographed. Synthetic frames therefore extend a scene coherently but less faithfully than the splats where photographs exist. They should count only where no real view covers the surface, carry the inferred label, and come from passes conditioned on real photos alone. Next: a second pass walking backwards from frame 0, to meet this one across the 133-199 degree remainder, then real plus registered synthetic frames through depth, fusion and the TSDF with the synthetic frames down-weighted, judged by `unseen_shape.py` against the held-out photographs.

**Where photographed surface is lost: the depth models, on transparent and dark surface (2026-10-27, `recon/evaluation/diagnostics/lost_surface.py`).** The new diagnostic samples the reference surface, keeps the samples the capture saw but the final mesh misses by more than 3 mm, and checks each stage in pipeline order. In the frames that see a sample, does VGGT or DA3 put depth within 3 mm; then the fused depth, the refined depth, the Gaussian pass's depth and the consistency-checked depth; then whether it is accurate in the TSDF's minimum of 3 views, and whether it survives the TSDF, extraction and the cut. The first check that fails is where the sample was lost. On the full-quality scene-first jeep (`runs/real/scenefirst_weighted/jeep`), 7.16% of the surface is seen but lost: **5.01% at the depth models** (neither within 3 mm in any view), 1.02% at fusion (one model had it and the photometric choice took the other), 0.60% at the Gaussian pass, 0.19% at refinement, 0.15% short of 3 accurate views, 0.10% at the cut, and 0.10% across consistency, the TSDF and extraction. Seventy percent of the loss happens before our stages run, and everything from fusion to the cut costs about 2% together.

The surface the depth models lose is seen by a median of 2 frames (22 for surface that is reconstructed), at a best angle of 57 degrees (36), with image brightness 29 (98). By brightness, the darkest fifth of the jeep loses 18.1% of itself, the brightest half 0.2%. Thin parts (under 5 mm) lose 27-32% but are only 2.6% of the surface. Projected onto the frames that see the most of it, it is two things: the **tinted transparent windscreen**, whose depth both models measure through to the cab and the rug behind it, and the **dark wheel arches and tyre-side recesses**, black plastic in shadow glimpsed obliquely. Neither is generative fill's job, because a generator is conditioned on the same photographs. The windows are bounded openings in an otherwise closed shell, which is what closure spans when it is allowed to run. The recesses are a depth-model weakness on dark, low-texture surface at grazing angles, and the 2026-10-12 fusion ceiling already showed a better selector has little left there.

**Where a run's time goes, and two safe speed-ups (2026-10-27, `runs/real/dev/jeep_profile`).** A default jeep run (43 frames) takes about 252 s, three quarters of it on the GPU. The GPU stages: the planar-Gaussian optimiser 101 s (40%), DA3 / VGGT / MoGe 50 s, the TSDFs 13 s, refinement, fusion, consistency and point clouds about 25 s. The CPU stages: COLMAP mapping, most of the 34 s pose stage, and texturing, 23 s. Comparing each stage's wall time with the compute time it reports, about 40 of the first pass's 122 s is overhead: chiefly the three depth models' processes starting up and loading weights (DA3 7.9 s, VGGT 7.1, MoGe 4.8, of which 4.5 / 5.1 / 3.1 s is the load). One resident process for all three would save most of that, but CLAUDE.md keeps each non-commercial model in its own stage, so that is not taken.

- *Optimiser:* `gaussian_refine.py` read its loss terms back to the CPU every step (`float()` of CUDA tensors, plus a median and an `.any()` in the multi-view loss, and the gate's `use.sum()` twice) only to feed a progress line that `--log-every 0`, the pipeline's default, never prints. They are now read only when logging, and the gate counts once. Training time 95.9 / 94.1 s -> 94.0 / 93.3 s on identical inputs, about 1.5% (the GPU was already at 96-97%). Output differs from the old code by exactly the run-to-run nondeterminism of the rasteriser's backward pass (median relative depth difference 7.5e-4 between any two runs).
- *Weighted TSDF:* each frame's preparation - loading, the pixel filter, agreement and angle weights, the image - does not depend on the robust pass but was redone in each. It is now done once and reused: 10.8 -> 6.4 s, with a bit-identical mesh (56,872 vertices, triangles and colours equal).

Texturing was measured but left alone. Of its 25.6 s, 12.3 s is Open3D's `project_images_to_albedo` running at about three cores, and 6.5 s the xatlas unwrap. Splitting the projection across threads would average batches with equal weights instead of Open3D's per-image blend and so change the texture; the real fix is a GPU bake built on `texel_points`, which needs the appearance judges before adoption.

**The GPU texture bake is the default (2026-10-27, `recon/surface/texture.py --bake gpu`, `runs/real/dev/texture_bake/`).** `bake_gpu` replaces Open3D's CPU `project_images_to_albedo`. Each atlas texel finds its triangle and barycentric weights from one ray per texel cast at the UV triangles laid flat (`texel_faces`; Embree, a fraction of a second where the per-triangle loop of `texel_points` takes seconds). Each texel's surface point is projected into every photograph on the GPU, kept where it is the first surface on the ray (a ray-cast depth map of the mesh agrees to 0.5% of depth), sampled bilinearly at full resolution, and weighted by cos(view angle)^4. Charts are then padded four texels outward with their own edge colour. Without the padding, texels on chart borders - whose centres fall just outside their triangle - stay black, read as 41% blank surface, and bleed into the model as dark seams. Open3D's albedo runs its rows the other way; the bake matches it (mean difference 7.8 levels flipped, 86-89 in every other orientation), because the fills, provenance and glTF writer are built on that order. Scored against the photographs neither bake used (`unseen_colour`, the frames outside the 24 projected), mean colour error Open3D -> GPU: development jeep 16.22 -> 14.58, audi 16.45 -> 15.56, convertible 23.33 -> 21.60, big_ben 23.62 -> 17.88. On the 14 validation scenes it is **lower on all 14**: mean change -2.26, median -1.99, blank surface 4.35 points lower on average (castle 17.53 -> 2.92%). The weighting power was chosen on jeep: 1, 4 and 16 gave mean errors 14.67, 14.58 and 15.86, the largest power leaning too hard on single views. The bake itself takes 6.8-7.1 s against Open3D's 12.1-12.8 s. On large meshes the stage's cost is now the xatlas unwrap: 40 s at 163k faces and 60 s at 300k, almost all chart computation (packing options save 3 s, larger charts 8). Unwrapping spatial chunks in parallel is the open fix. `--bake open3d` keeps the old path.

**The depth models in one process (2026-10-27, `recon/depth/batch.py`, `DEPTH_BATCH`, default on).** At the user's request, MoGe, VGGT and DA3 run as jobs in one process, model by model. Each model is loaded for the first job needing it, reused by later jobs with the same weights, and dropped - deleted, its CUDA cache emptied - after the last queued job that needs it: on a single scan as soon as its stage is done, over a batch only after the last scan. Each stage keeps its own module and its own summary, which now records `load_s` and `inference_s` separately; the batch writes both per stage to `depth/depth_batch.json`. On one jeep scan, depth takes 49.0 s against 52.8 s as separate processes (load 14.6 s: MoGe 4.0, VGGT 5.8, DA3 4.7; inference 31.7 s), so only start-up is saved. VGGT and DA3 come out bit-identical (43/43 frames each); MoGe differs by up to 1.6% relative depth, but two separate-process MoGe runs differ by the same 1.56e-2, so that is MoGe's own nondeterminism. `make benchmark` now solves every scene's poses first, collects each scene's jobs with `make depth-jobs`, and runs them all in one batch before the per-scene pipelines, which find their depth built (`--no-depth-batch` turns this off). On jeep and audi, each model loaded once (MoGe 3.4 s, VGGT 5.3 s, DA3 10.0 s), was dropped after audi's last job, and no depth stage ran inside either scene's pipeline. Jeep scores official F1 90.11 and chamfer 2.846 mm either way (separate processes 90.11, 2.847).

**Video Depth Anything assessed: our depth is already at its temporal floor (2026-10-27, `recon/evaluation/diagnostics/temporal_consistency.py`).** Video Depth Anything (Chen et al., CVPR 2025) freezes Depth Anything V2's encoder and adds temporal self-attention per pixel position to the head, trained with temporal gradient matching (the same pixel's depth change between consecutive frames matched to the truth). Long videos run in 32-frame windows whose scale and shift are aligned through overlapping frames and keyframes. Its consistency metric, TAE - each frame's depth warped into the next with the camera motion, AbsRel there, both ways - needs poses, which we have, so the diagnostic computes it per depth stage. With `--scene` it also scores the reference mesh rendered into our cameras, the floor that poses and pixel rounding put under any depth. On object pixels, jeep / convertible (the glossy one): MoGe 2.36 / 3.56%, VGGT 0.51 / 0.60%, DA3 0.49 / 0.57%, fused and refined 0.55 / 0.71%, **planar-Gaussian pass 0.151 / 0.161%, cross-view checked 0.147 / 0.150%, floor 0.107 / 0.153%.** The raw models do swim more on the glossy scene, but the Gaussian pass, one 3D model rendered into every frame, takes it to the floor (on convertible to within noise of it). It does in 3D with known poses what VDA's head does in 2D. Per-frame scale and shift is not where the raw inconsistency lives: correcting each frame pair with its best scale leaves DA3 at 0.467% from 0.494%. Neither a temporal head nor VDA-style window alignment has anything left to remove. The remaining blur is depth that is consistent but consistently smooth, an accuracy limit, not a consistency one.

**Highlights: a single-image remover fails on white LEGO, a multi-view one does not (2026-10-27, `recon/depth/fusion/highlights.py`, `make highlights`, `HIGHLIGHT_FREE=1`).** TSHRNet (Fu et al., ICCV 2023; albedo-shading decomposition, refinement and tone correction trained on the synthetic SSHR set, mixed-data checkpoint; no licence stated) was tried on glossy frames with its correction applied to the full-resolution photograph. It removes the reflection on the ferrari's dark windscreen, but it greys the convertible's white stripes and the jeep's white roof: from one photograph a white brick and a highlight are indistinguishable. It was not adopted. A capture does not have to guess: a highlight moves across the surface as the camera moves, a white brick is white in every frame. `highlights.py` takes the classic multi-view separation (Lin et al., ECCV 2002) with the pipeline's own correspondence. Each pixel with cross-view-checked depth is projected into its 8 nearest same-facing frames, occluded views are dropped (1% depth test), each view's exposure is matched to the frame by the median luminance ratio, and the consensus colour is the median luminance across views. Pixels brighter than that by more than 0.06 with at least 3 views take the consensus, feathered, and the correction is applied to the full-resolution photographs. On convertible and jeep it leaves white stripes and the white roof untouched and removes the windscreen glare, chrome glints and the streaks on the jeep's tan panel: 6.0 and 7.4% of depth pixels. It runs in 3.7 s for 63 frames, with every working frame held on the GPU once and disk I/O on worker threads (16.9 s before, re-reading each neighbour per frame; output within one grey level). Baked into convertible's texture, it changes 5.8% of the atlas by more than 10 levels, restoring saturation that averaged glare had washed out, with held-out colour error unchanged (21.56 both, scored against photographs that keep their highlights). Opt-in, for texturing only. Fed to the photometric stages it changes no geometry (`runs/real/academic/highlight_geometry.sh`, `runs/real/dev/highlight_geometry/`). Per development scene there are two arms with the same poses and the same depth-model outputs; in arm B fusion, refinement, the planar-Gaussian pass and the TSDF read specular-free frames made from arm A's depth, while the depth models read the original photographs in both. The changes are: official F1 jeep -0.24, audi -0.05, convertible +0.16, big_ben +0.24 (mean +0.03); F@1 -0.32 / -0.66 / +0.20 / +0.12 (mean -0.17); shape median +0.001 / +0.003 / -0.005 / -0.005 mm. The glossy scenes move slightly the right way and the matte ones slightly the wrong way, all within run-to-run noise. Highlights cover 3.1-6.5% of depth pixels, and the photometric stages already tolerate them - NCC normalises brightness, the Gaussian pass gives colour a view-dependent term, and its depth sits at the temporal floor - so there is nothing for specular-free images to recover in the geometry.

**Concave and convex errors: recesses are filled in by the majority of views (2026-10-27, `recon/evaluation/diagnostics/signed_error.py`).** Unsigned metrics cannot tell a filled recess from a sunken panel. The diagnostic samples the reference, casts along each sample's outward normal to our mesh, and reports the signed offset. It first refines placement and scale by ICP, as the shape metrics do: without that, convertible's +1.40% scale error read as 30.9% of the surface "dented" (median offset -1.72 mm). After refinement every development scene's median offset is within 0.07 mm of zero. Beyond 2 mm: jeep 3.5% dented and 2.8% bulged, audi 6.6 / 4.2%, convertible 10.3 / 7.9%, big_ben 9.2 / 13.6%, typically 4-10 mm deep, so these are discrete wrong regions, not warping. Both are rarer on surface seen head-on than at grazing angles or by 1-3 frames. Marked on the photographs, there are three kinds: recesses filled in (jeep's wheel hubs and arches, convertible's open cockpit), sharp convex edges rounded off (thin dents along body edges), and windows (the depth models measure through the glass).

Measured against the reference's own geometry - openness, the share of 32 hemisphere rays that leave within 5 cm, and the distance to the nearest edge where faces meet beyond 60 degrees - **80-89% of bulges lie in recesses** (openness under 0.5) on all four scenes. Recesses are 18-40% of the surface and are bulged at 14.5-31.1%, against 0.2-2.4% on open flat surface, which is nearly perfect except convertible's dents (10.6%, the windscreen and dark glossy panels). Dents split between recesses and rounded edges (32-62% within 2 mm of a sharp edge).

Stage by stage, at the bulged recess samples of jeep / big_ben, every stage's depth lies in front of the true recess floor in most of the views that see it (VGGT 85.5 / 80.1%, DA3 86.7 / 70.6%, refined 83.3 / 87.1%, Gaussian 75.4 / 83.5%). A plausible reason is the models' resolution: a 5 mm recess spans about 21 px of a full-resolution photograph but about 6 px at the 518-756 px the models process. A minority of views do reach the floor within 2 mm, and refinement reaches it most often (46.7 / 62.1% of samples in at least one view). The planar-Gaussian pass then votes those views down, to 38.3 / 36.8%: one model consistent with every view follows the majority, so the same consistency that removed flicker flattens recesses. The evidence for most recesses is in the data, held by the few views that look into them, and averaging or majority fusion discards it. Two directions follow: visibility-aware weighting, which trusts the views that look into a hollow for that hollow, in the TSDF or in the Gaussian pass's depth supervision; and free-space priority (space carving), where a confident view that has seen through a point empties it, at the risk of carving real surface from noisy depth. Windows are a separate and smaller share; no photometric method measures glass.

*Free-space priority in the TSDF does not recover them (rejected, 2026-10-27, `runs/real/dev/behind_band/`).* In a recess the views that see only its rim vote solid for the whole band behind their surface - the hollow - and outnumber the view that sees through to the floor and votes it empty. So the weighted TSDF was given a shorter band behind each view's surface than in front (`--behind`, the fraction counted behind), re-fusing the default run's depth on the development scenes. At 1.0 / 0.5 / 0.25: jeep official 92.79 / 92.91 / 84.80, F@1 82.27 / 82.06 / 76.03, shape 0.253 / 0.266 / 0.287 mm, roughness 0.0248 / 0.0281 / 0.0407, recess bulged 23.1 / 22.3 / 25.2%. Big_ben: official 77.97 / 77.72 / 73.82, F@1 51.07 / 50.14 / 44.43, recess bulged 34.0 / 32.2 / 30.1%. Audi and convertible follow suit. The recesses move by at most four points while everything else degrades: depth noise carves holes into real surface faster than the few floor-seeing views open the hollows. By the time the TSDF runs the evidence is mostly gone, because the planar-Gaussian pass has already voted those views down (big_ben 62 -> 37%), so a recess fix has to act in or before that pass. Removed.

*Free space in the planar-Gaussian pass does not recover them either: the deeper first-pass readings are noise, not floors (rejected, 2026-10-27, `runs/real/dev/free_space/`, `runs/real/academic/free_space.sh`).* The pass was given a one-sided term: wherever its render lay more than a tolerance in front of the first-pass refined depth (relative shortfall, capped at 2%), it was penalised, counting only first-pass pixels no neighbouring view sees through and at least one confirms. The tolerance was set above the noise: the refined depth sits 0.1-0.2% behind the default pass's depth on average, with its 95th percentile at 1.0-1.3%, so at 0.5% the term would have pushed the whole surface back; 1% is 2.6-4.9 mm on the development scenes. It did what it asks - pixels more than 1% in front fell from 5.23% to 2.14% (weight 1) and 0.91% (weight 10) - and the meshes got worse, recesses included. Jeep, control / weight 1 / weight 10: official 93.00 / 91.83 / 91.07, F@1 82.25 / 79.72 / 76.87, shape median 0.255 / 0.295 / 0.371 mm, recess bulged 22.4 / 23.8 / 25.4%, open surface dented 2.3 / 3.5 / 5.1%. The reason is the evidence. Traced to the reference, where the first-pass depth is more than 1% behind the render it is the wrong one: 2.92 mm behind the true surface (median), against 0.66 mm in front for the render, which is closer to the truth at 73.5% of those pixels. And only 7.5% of them are in recesses, the same as object pixels overall (8.3%). The 47-62% of bulged recess samples that some first-pass view reaches is real, but per pixel those readings cannot be told from the overshoots around them. Code removed.

*Monocular normals do not see them either (2026-10-27, jeep, scratch probe).* Normals change sharply at a recess wall where depth barely moves, so a normal estimator could in principle find recesses that depth smooths over. MoGe-2's normal model (`Ruicheng/moge-2-vitb-normal`, full-resolution photos, `resolution_level` 9) against the reference's normals, every sixth frame: median angular error in recesses 36.5 degrees (p75 53.7), on open surface 14.6, against 42.0 (p75 67.0) and 18.2 for normals of our final depth. It is better everywhere by a few degrees and still badly wrong in recesses, so it cannot carve them. With depth, refinement, free space, resolution (above) and normals all falling short, recesses at this scale are beyond the evidence the current models extract. The photographs hold them as shading, which the texture carries.

*Fine-detail monocular models are far behind our multi-view depth in recesses (2026-10-27, scratch probe `recess_probe.py`).* Each candidate's depth on every sixth frame was fitted to the reference depth by a per-frame scale and shift - an oracle alignment, so only shape is judged - and scored at full resolution away from the silhouette, split by openness; "recovered" is the median share of each recess's true depth below the surrounding open surface that the candidate reproduces, over pixels whose true recess is deeper than 2 mm. Jeep / big_ben: our final depth 0.74 / 2.34 mm in recesses, 0.66 / 1.68 mm on open surface, recovering 74 / 96%; MoGe-3 (sparse 3D refinement, the fine-detail model) 2.67 / 10.53 and 2.52 / 7.60 mm, 56 / 65%; MoGe-2 3.90 / 15.00 and 3.25 / 11.13 mm, 35 / 56%. Predicted normals are a few degrees better than our depth's in recesses (MoGe-3 34.5 / 33.0 against 40.7 / 40.5 degrees) but nowhere near usable. Even aligned by the truth, single-image depth is three to six times worse than the fused multi-view depth, so feeding a sharper monocular model into fusion cannot recover recesses. Per pixel our depth already reaches most recess floors; what bulges is the minority of recess surface (22% on jeep) that most views see only past the rim. Pixel-Perfect Depth (Xu et al., NeurIPS 2025 / TPAMI 2026, Apache-2.0; pixel-space diffusion, 4 steps, about 0.8 s a frame at 1024x768; `third_party/pixel-perfect-depth`, checkpoints in `runs/models/ppd`), fitted the same way as depth or as disparity, whichever is closer: with Depth Anything V2 semantics jeep 4.41 / 3.98 mm (recess / open), recovering 31%, big_ben 14.64 / 12.37 mm, 54%; with MoGe-2 semantics jeep 2.85 / 2.76 mm, 50%, big_ben 11.62 / 9.64 mm, 75%. RoSE (Li et al., ICLR 2026, `third_party/RoSE`, no licence stated, on SV3D under Stability's community licence; probe only), the best published object-normal estimator (it generates the object under nine lights and solves photometric stereo on the result), was run on the object masked onto black and cropped square at 576 px, about 9 s a frame. Its normal maps look the sharpest of all - separate studs, grille slats, hubs - but measured against the reference they are the least accurate: median error in recesses 41.3 / 44.8 degrees (jeep / big_ben, p75 68), on open surface 22.5 / 31.5, against MoGe-3's 34.5 / 33.0 and 13.3 / 18.6 (axis convention checked over all 48 permutations and signs). **RoSE normals as a per-view prior in the planar-Gaussian pass: cleaner panels and better shape metrics on the development scenes, rejected because it loses parts (2026-10-27/28, `runs/real/dev/normal_prior/`, `runs/real/dev/normal_prior_val/`, `runs/real/academic/normal_prior.sh`, `normal_prior_val.sh`; code removed).** The per-pixel scores above miss what the eye sees: RoSE's normal maps are clean and piecewise flat with sharp edges, where ours are covered in speckle. Two corrections to that scoring. First, the reference's own normals ripple: the CAD meshes are remeshed at about 1 mm, so face normals on flat panels vary by several degrees; interpolated vertex normals remove that. Second, the reference sits 2-4 px off the photographs for every source, so per-pixel detail scores are mostly misregistration. RoSE's error is global: its maps are tilted 14-19 degrees per view (MoGe-3 3-6) and sheared (the bas-relief ambiguity of photometric stereo), and a 3x3 linear fit per frame brings jeep from 23.4 to 16.2 degrees (MoGe-3 13.5 to 11.8).

So RoSE cannot be used as is, nor averaged across views: fusing corrected maps per mesh face and moving the vertices onto them crinkled the surface, because views disagree; using them only as the range guide of a joint bilateral filter on our own normals (after Zhang et al. 2015) flattened panels (open-surface face error 11.9 -> 9.3 degrees) but merged studs into ridges. What works is to compare each view's map only with that view's render inside the optimiser. `NormalPrior` refits the map to the rendered normals by a 3x3 linear map every step (detached, so only its local structure is used) and adds 1 - cos to the rendered normal and to the normal of the rendered depth on object pixels; the photometric and multi-view terms reconcile the views. RoSE runs per frame on the object masked onto black, cropped square at 576 px (about 9 s a frame), its maps resized to the working frames.

Jeep, against a control built from the same inputs (official / F@1 / shape median): control 93.00 / 82.25 / 0.255; weight 0.2 84.67 / 70.06 / 0.422 (over-flattened); 0.05 92.29 / 82.57 / 0.301, visibly cleanest panels but studs flattened; 0.02 92.85 / 84.60 / 0.263, panels clean and studs round and regular; 0.05 on the depth normal only 92.16 / 82.34 / 0.282; 0.05 from step 1000 92.62 / 83.73 / 0.281; MoGe-3 at 0.2 90.66 / 77.80 / 0.375. **RoSE as a baked normal map: cleanest look, geometry untouched, rejected for accuracy (2026-10-28; code removed).** After the prior was rejected for losing parts, the same normals go where a wrong normal can only change shading. **Feature-preserving denoising after cleanup (2026-10-27, `recon/surface/denoise.py`, `DENOISE=1`, default; `runs/real/dev/denoise_final/`).** Flat panels came out covered in millimetre bumps and pits from view-to-view depth disagreement, and they fail an eye test even where the metrics are good; Taubin smoothing removes them only by rounding creases too. Bilateral normal filtering averages each face's normal with its neighbours', weighted by distance and by how alike the normals already are, so faces across a crease barely mix; the vertices are then moved onto the filtered faces' planes. The settings were chosen by eye on close-ups against the reference (jeep's grille and side panel, convertible's cockpit): range 0.35 with 10 or 20 normal iterations merged the hood's studs into ridges, because a reconstructed stud is a bump the size of the noise, while range 0.2 with 4 iterations smooths the panels and keeps studs, seats and creases. Two failure modes were fixed on the way. Unconstrained vertex steps turned 1.4% of jeep's faces inside out (dark specks); the update now undoes any step that flips a face. About 1% of faces were wound against their neighbours and steered the filter; faces are oriented first. Flipped faces relative to the input are 0.73%, mostly the input's own folds. The metrics barely move, as expected of millimetre noise: official F1 jeep 92.79 -> 92.75, audi 89.66 -> 89.60, convertible 60.56 -> 60.42, big_ben 77.97 -> 77.81; F@1 82.27 -> 82.28, 79.23 -> 79.10, 52.33 -> 52.41, 51.07 -> 50.92; shape median 0.253 -> 0.248, 0.335 -> 0.342, 0.576 -> 0.566, 0.532 -> 0.533 mm. Adopted for appearance, at the user's direction that eye tests decide. It does not touch the filled recesses or the windows, which are depth errors, not noise. *Checked against the acceptance rule - accurate, smoother by eye, no lost sections (2026-10-28, `runs/real/dev/denoise_check/`).* Lost surface (reference surface the undenoised mesh has within 1 mm and the denoised one has nothing within 3 mm) is 0.00% on jeep, audi, convertible and big_ben, and on motorcycle and london_bus, chosen for their thin parts; face counts and boundary edges are identical (the stage moves vertices, never removes faces), and area falls 0.9-1.1%, the bumps flattened. Motorcycle's handlebars and mirror stalks are intact by eye. Motorcycle official 95.09 -> 95.02, F@1 81.10 -> 80.90, shape median 0.372 -> 0.371 mm; london_bus 55.73 -> 55.44, 60.89 -> 60.77, 0.623 -> 0.622. 1. **Meshing:**
   - Settings explored (see "Where the remaining error is"); nothing beats the current wide-band TSDF on today's depth.
   - A confidence-weighted dense object TSDF is built (`surface/weighted_tsdf.py`). Per-pixel weights come from VGGT–DA3 agreement (σ 1%) times viewing angle; band 0.06; whole-image depth carves free space.
     - **Weights also gating surface:** accuracy up a lot (convertible shape 0.719 / 3.016 to 0.567 / 2.252) but coverage down (convertible 79.8% to 69.7%), and F-score down on 2 of 4 scenes.
     - **Weights only averaging, surface needs 3 views (`--min-views`):** F-score above the default on all four scenes at 1 and 2 mm (+0.3 to +2.6 points), but shape median and p90 worse because more hard surface is kept.
     - **Adopted as the default object surface** (2026-10-10): `OBJECT_TSDF=weighted`, band 0.06, σ 1%, angle weight, 3 views.
     - **Robust second pass** (default `--robust-passes 2 --robust-scale .5`): each observation is re-weighted by its agreement with the first pass (iteratively reweighted averaging). Development F@1mm went +0.3 / +0.5 / +0.5 / +1.1 (jeep, audi, convertible, big_ben); F@2mm stayed within ±0.2 except big_ben (+1.1).
   - Recall is the weak side: 26–68% at 1 mm against 56–88% precision.
   - `diagnostics/recall_loss.py` (removed 2026-10-12, archived) attributed missed reference surface to its first failing stage. On jeep (recall 70%), the 30% missed breaks down as:
     - truly absent, about 8%: unobserved 6.7%, outside mask 0.9%, holes 0.8%;
     - "almost there", 21%: depth present but more than 1 mm off 12.0%; accurate depth in at least 3 frames but the fused surface 1–3 mm off 9.4%, because averaging includes the off frames.
   - Recall at 1 mm is therefore mostly an accuracy problem near the threshold.
   - Current default on jeep (`runs/real/dev/jeep/base`, 2026-10-12): recall 70.5%; missed: inaccurate depth 11.4%, unobserved 6.8%, meshing 1–3 tolerances away 8.0%, removed by cross-view check 1.6%, outside mask 0.9%, no surface nearby 0.9%.
   - **Photometric mesh refinement (tried 2026-10-12, rejected; code archived as `refine_mesh.py`):** each vertex searched ±0.6% of depth along its normal for the best slanted-patch NCC between its best-facing view and 6 neighbours 10–35° away (best 3), displacement smoothed over the mesh. On jeep every variant lost: F@1 75.7 → 71.6 without pooling, 65–67 with the score curves pooled over the mesh neighbourhood; shape median 0.37 → 0.54–0.62 mm. Diagnosis: refining the reference CAD mesh itself (placed in our frame) moved it by a median 0.67 mm with no net bias, so the photometric optimum scatters by more than our surface error. At our camera accuracy (centres off by 0.5–1 mm) per-vertex photo-consistency cannot place the surface to better than about half a millimetre; it helps depth only as a choice between hypotheses pooled over image windows (fusion), not as a free refinement. Also found: the object meshes' triangle winding faces inward, so ray-cast visibility needs per-vertex normal orientation (flip towards the cameras that see the vertex).
2. **Remaining depth gap:** more independent multi-view models. Tested so far:
   - **MapAnything** (`multiview/mapanything.py`, removed 2026-10-12): 3.9 mm per-pixel median against about 1.3 for VGGT and DA3, with or without our cameras. Rejected.
   - **π³X** (`multiview/pi3.py`, removed 2026-10-12): 1.35 mm. As a third fusion candidate it gave −2 to −4% on three scenes and +3% on jeep, so it's not adopted yet.
   - **VGGT-Ω** (`multiview/omega.py`, 2026-10-12): the gated, retrained 416 px checkpoint is available as an opt-in candidate (`OMEGA=1`) or VGGT replacement (`DEPTH_MODEL=omega`). On the four development scenes, VGGT+DA3 / Ω+DA3 / all three gave F@1mm: jeep 75.68 / 76.21 / 75.95; audi 71.60 / 70.01 / 72.46; convertible 45.22 / 42.79 / 45.55; big_ben 38.46 / 37.18 / 38.81. The three-model filter selected Ω for 16–25% of object pixels and improved F@1mm on all four by 0.27–0.86 points. The 18-scene holdout has not been run, so the default remains VGGT+DA3. Results: `runs/real/omega_416_sweep/`, `runs/real/omega_fusion_416_sweep/`.
     - **Depth accuracy** (later 2026-10-12, `diagnostics/fusion_ceiling.py --extra omega`), per-pixel median on object pixels: jeep 1.87 mm (1.54 with the 512 checkpoint) against VGGT 1.27 and DA3 1.18; audi 1.72 vs 1.47 / 1.32; convertible 2.75 vs 2.22 / 2.10; big_ben 6.18 vs 3.89 / 2.96. Worse than both on its own; it helps the fusion only where it is the one that is right. 17–34 s per scene. Package now pinned (vggt-omega 48b23c8, `make setup-omega`) instead of the `third_party/` clone.
     - **Cameras** (`cameras/feedforward.py`: one pass, the package's `encoding_to_camera`, principal point at the centre), against our COLMAP: centre error 2.1–3.2 mm on DTU scan24/37/63 (COLMAP 0.86–1.22) and 5.4–10.3 mm on the MobileBrick dev scenes (COLMAP ~0.8); median relative rotation 0.59–0.90° on DTU, 1.4–1.8° on MobileBrick (COLMAP 0.27–0.45°); focal +2.6 to +6.3% (COLMAP within ±1.5%). Not a replacement for our cameras; plain VGGT's rotations beat Ω's on scan24 (0.28° vs 0.59°). On jeep VGGT and Ω are alike (centre 5.30 / 5.43 mm, AUC@3 46 / 43, AUC@30 93 / 93), so the decoding is sound: their accuracy shows at AUC@30, not at our millimetre scale.
     - **Camera slot** (2026-10-12): `CAMERAS=omega` runs `cameras/feedforward.py` and keeps Ω's cameras fixed while COLMAP triangulates our matches (`solve.py --init-cameras … --init-rounds 0`); `CAMERAS=omega_ba` adds `CAMERA_ROUNDS` (6) rounds of bundle adjustment and re-triangulation (`sfm.initialised_model`) in place of incremental mapping. jeep through `make poses`: colmap 0.84 mm / AUC@3 98.45 / 0.27°; omega 5.43 / 42.67 / 1.62°; omega_ba 0.85 / 98.34 / 0.285°.
     - **Ω as COLMAP's starting point** (experiment: our database's SuperPoint/LightGlue matches triangulated with Ω's cameras fixed, then bundle adjustment with focal refined; repeated rounds re-triangulate with the refined cameras). jeep, against COLMAP's own shared-focal model: 1 round 2.56 mm / AUC@3 79.6 / 0.74°; 3 rounds 1.71 / 97.0 / 0.30°; 6 rounds 1.58 / 97.3 / 0.30° (COLMAP 1.58 / 97.4 / 0.28°). DTU scan37: 1 round 2.13 mm / 86.1 / 0.62° / focal +2.0%; 6 rounds 1.33 / 96.7 / 0.47° / −1.25% (COLMAP 1.22 / 98.2 / 0.45° / −1.5%). Both starts converge to the same bundle-adjustment optimum: camera accuracy is limited by the matches and the camera model (fixed principal point), not by initialisation, so Ω cannot improve it. What Ω could offer is speed and robustness on long captures: one ~3 s pass plus ~15 s of triangulation and adjustment for 49 frames could replace incremental mapping (the whole COLMAP stage took 62 s on scan37, features and matching included), and every frame gets a camera even where incremental mapping would split the sequence. Not built.
     - **Register-only attention** (the paper's 6%-FLOP variant, trained that way; the release keeps global attention in all inter-frame blocks except 2, 6, 9, 14, 20): switching the released weights to register-only at inference (`feedforward.py --register-only`) breaks them (jeep rotations ~90° off, focal +47%) while halving the forward time (2.9 → 1.4 s for 43 frames). Usable only with the paper's register-only checkpoint, which is not released; for us it would give single-pass cameras for captures longer than the 128-frame global pass.
     - **Three-way fusion with 3 refinement passes** (`runs/real/dev/<scene>/tri_omega`), F@1 against two-model fusion with 3 passes: jeep −0.91 (precision −2.40), audi +0.44, convertible −0.30, big_ben +0.30. The one-pass gain above disappears once refinement runs three passes. The scene-adapted DA3 alone (`adapt_da3only`) beats both everywhere: F@1 +1.10 / +1.54 / +1.44 / +2.99, refined depth median 0.80 / 0.90 / 1.43 / 1.91 mm against 0.95 / 1.03 / 1.73 / 2.17 with Ω. Ω is not adopted for depth or cameras.

3. **Reflections:** MVInverse (feed-forward multi-view albedo, CVPR 2026; `fusion/intrinsics.py` (removed 2026-10-12), needed 8-frame windows on 24 GB) was tested and rejected.
   - Its albedo removes highlights and is view-consistent, but it is produced at about 1022 px and is smoother than the photos.
   - Perfect-depth discriminability on glossy convertible rose only from 25% to 27% (jeep, non-glossy: 33% with RGB).
   - End to end it was worse: convertible fusion+refinement 0.909 / 3.097 mm against 0.740 / 2.746 with RGB; jeep 0.410 / 1.438 against 0.338 / 1.214.
   - Its shading does not reproduce the image when multiplied by albedo (scale or colour-space mismatch), so the residual and de-lit outputs are unusable.
   - **Less lossy "ratio albedo"** (`ratio_albedo/`): the albedo/image ratio is computed at model resolution, upsampled, and applied to the full-resolution photo. It keeps the photo's texture and suppresses highlights.
     - With the current pipeline (weighted TSDF, DA3 at 756): convertible F@1/F@2 47.4/66.5 with RGB, 47.9/66.9 with ratio albedo; p90 2.537 to 2.462 mm.
     - On jeep (matte) it was slightly worse: F 75.5/89.5 to 74.5/89.2.
   - **Albedo only in troubled areas** (`material/` holds roughness and metallicity): blending to ratio albedo where roughness < about 0.3 switched only 0.8% of convertible's pixels (the windscreen), giving F 47.7/66.8.
   - Net: about ±1 F-point for 50–90 s of MVInverse per scene (4–8-frame windows while other GPU jobs run), so it's not adopted. A better trouble mask (metallicity marks the whole glossy car) bounds the gain at the ratio-albedo result above.

Without masks the scene is reconstructed. This project must not ship or reference any particular mask generator.
